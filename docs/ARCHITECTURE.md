# Архитектура klgpff

Описание кода, как он есть в репозитории. Цифры из прогонов и логов помечены датой. Что я не проверял, написано прямо.

## Из чего состоит

Python 3.11, `python-telegram-bot` (polling), Anthropic SDK напрямую, Voyage для эмбеддингов, Postgres 16 с pgvector для поиска по фактам, остальное состояние в файлах. Один процесс, один контейнер. Postgres общий: контейнер `nexus-arcana-db`, у бота там своя база `klgpff` и своя роль. Бот подключён к docker-сети этого контейнера.

```
Telegram → handler
         → режим модели (по умолчанию opus; auto запускает роутер на Haiku)
         → факты: все, если их не больше FACTS_FULL_LIMIT, иначе поиск в pgvector
         → память сцен: top-k чанков сохранённых сцен (если есть)
         → system (статичный) + история + канон и справка из сцен в хвосте последнего сообщения
         → Anthropic Messages API, стриминг
         → ответ порциями до 4096 символов
```

## Путь одного сообщения

1. Проверка белого списка `ALLOWED_USERS`. Если переменная пуста, бот открыт всем.
2. Документ в модель не идёт никогда: в режиме `/import` или `/prompt` это часть буфера, вне режимов отказ (раньше `.txt` уходил прямо в `_process_user_text`, мимо порога длины). Сообщение в режиме `/import` или `/prompt` и сообщение, пересланное от самого бота, в модель не идёт: уходит в буфер частей (см. «Память сцен» и «Длинный запрос»). Обычное сообщение длиннее `MAX_INPUT_CHARS` (4000) получает отказ без вызова модели. Единственный путь длинного текста в модель: `/go` после `/prompt`. Если дневной лимит исчерпан, отказ тоже без вызова. Иначе текст сообщения (или содержимое присланного `.txt`) добавляется в историю, история обрезается.
3. Режим модели читается из `models/<chat_id>.txt`. Нет файла: opus. Режим `auto`: вызывается классификатор.
4. `get_relevant_facts` возвращает факты и строку `source` для лога. `get_memory_scenes` возвращает фрагменты сцен (пусто, если сцен нет или поиск упал).
5. `build_messages` собирает запрос (канон, затем блок `<memory_scenes>` в хвосте последнего сообщения), `system_block` оборачивает системный промпт.
6. Генерация идёт через `client.messages.stream`, `max_tokens` по умолчанию 32000. Стриминг нужен потому, что SDK отказывается от запросов без стрима, которые могут идти дольше 10 минут.
7. Из ответа `response_text()` склеивает только text-блоки.
8. Пустой текст: в историю ничего не пишется, пользователь получает «пустой ответ (stop_reason=...)», в ops-тред уходит предупреждение со `stop_reason`, usage и моделью.
9. Ответ режется по абзацам до 4096 символов и уходит сообщениями.
10. В лог пишется строка `done:` с числом символов, токенами, `cache r`/`w`, ценой и `scenes=<число подмешанных чанков>`.

Короткие вызовы (классификатор) идут без стрима.

## Модель и размышления

Opus 5.5 в `content` отдаёт `ThinkingBlock` первым блоком. Раньше код брал `content[0].text` и падал на блоке без `.text`. Сейчас везде используется `response_text()`.

Токены размышления в ответе не видны, но входят в `output_tokens` и оплачиваются как output. Косвенное подтверждение из лога 14.11.2026: ответ 1625 символов и `1.8k out`. Для русского текста такой длины это заметно меньше, остальное похоже на размышления. Точной разбивки API не даёт, поэтому это оценка, а не измерение.

Если при `stop_reason=max_tokens` текста нет, значит, весь бюджет ушёл на размышления. Бот в этом случае отвечает «пустой ответ» и не пишет ничего в историю.

## Кеширование

- `system` статичный: только текст системного промпта чата, с `cache_control` типа `ephemeral` и TTL 1 час (`CACHE_TTL`, можно `5m`).
- Канон в `system` не попадает. Его дописывает `build_messages` к концу последнего сообщения пользователя. Поэтому набор фактов может меняться от запроса к запросу, а префикс (system и история) остаётся тем же.
- Точка кеширования стоит на последнем ответе ассистента: кешируется всё до него. Канон в историю в памяти не записывается.
- История обрезается пачкой. Когда набирается `MAX_HISTORY` пар (8), остаются последние `HISTORY_KEEP` (4). При скользящем окне префикс менялся бы на каждом ходу и кеш не попадал бы никогда.
- Запись в кеш с TTL 1 час стоит два input, чтение пять или десять процентов input (см. цены).

Проверка по логам, 14.11.2026, sonnet, шесть запросов подряд: `cache r` каждого запроса равен `r + w` предыдущего (3355 + 750 = 4105, 4105 + 439 = 4544, 4544 + 541 = 5085, 5085 + 639 = 5724). 3355 токенов это системный промпт. Кеш растёт ровно на приращение каждого хода.

## Факты

Хранение. Источник правды: `facts/<user_id>.json`, JSON-список строк в порядке добавления. При каждой записи копия пишется в `backups/facts/<user_id>.json`. Если при старте рабочий файл пуст, а копия нет, файл восстанавливается из копии.

`/facts` показывает список в формате `N. текст`, где N это позиция строки в `facts/<user_id>.json` с единицы, то есть номер, который принимает `/forget`. Список режется на сообщения по границам фактов, не больше 3800 символов в сообщении (`FACTS_MSG_LIMIT`). Один факт длиннее 3800 символов режется по символам, остаток идёт следующим сообщением без номера. Если фактов нет, бот отвечает подсказкой про `/remember`.

Индекс. Таблица `facts` в базе `klgpff`: `user_id bigint`, `fact_index integer`, `fact_text text`, `embedding vector(512)`, первичный ключ `(user_id, fact_index)`. Эмбеддинги Voyage `voyage-3-lite` (512 измерений). Расширение `vector` создаёт админ БД, у роли бота прав на это нет. Индекс пересоздаётся целиком: при `/remember`, `/forget`, при восстановлении из копии и при первом обращении, если индекс пуст. Эмбеддинги считаются до транзакции, замена атомарна: если Voyage недоступен, старый индекс остаётся.

Поиск. Точный перебор по косинусному расстоянию (`<=>`), ANN-индекса нет. По комментарию в `rag.py` HNSW имеет смысл от десятков тысяч строк, у меня 132, замеров скорости я не делал. Запросов два: текущее сообщение (до 1500 символов) и контекст (две предыдущие реплики пользователя и первые 800 символов последнего ответа, всего до 2000). Первое сообщение чата даёт один запрос. На каждый запрос берётся 30 ближайших (`RAG_TOP_K`), результаты склеиваются без дублей, остаётся не больше 50 лучших (`RAG_MAX_FACTS`), порядок возвращается авторский, по `fact_index`.

Порог. Пока фактов не больше `FACTS_FULL_LIMIT` (150), поиск не используется, модель получает все факты, в логе `source` равен `all (<= 150)`. Сейчас фактов 132, то есть в проде поиск не работает вообще. Он включается, когда фактов станет больше 150, или при `FACTS_FULL_LIMIT=0`.

Деградация. Если БД недоступна или нет ключа Voyage, бот отдаёт все факты (`source` вида `fallback`) и шлёт предупреждение в ops-тред. Пустой индекс заполняется заново из файла.

Закреплённые факты. Факт, который начинается с маркера 📌 (например, `/remember 📌 у героини шрам`), закреплён. В `facts/<user_id>.json` он хранится как есть, с маркером, `/facts` показывает его тоже с маркером. Когда поиск включён (фактов больше `FACTS_FULL_LIMIT`), выдача собирается так: сначала все закреплённые в авторском порядке, потом результат поиска. Закреплённые исключаются из SQL-запроса по `fact_index`, поэтому не занимают места в `RAG_TOP_K` и `RAG_MAX_FACTS`: при трёх закреплённых и `RAG_MAX_FACTS=50` в промпт уйдёт до 53 фактов. Дублей нет: если индекс устарел, совпадающие по тексту факты отбрасываются. Маркер не попадает ни в канон, ни в текст для эмбеддинга (везде `strip_pin`: он убирает маркер и пробелы или variation selector после него). Если закреплённых больше 40, в лог пишется предупреждение. Пока фактов не больше `FACTS_FULL_LIMIT`, маркер ничего не меняет, все факты и так идут в промпт. В `source` закреплённые видны как `semantic (N queries) + K pinned`, без них формат прежний. Если все факты закреплены, поиск не вызывается (`all pinned`).

Закрепить уже существующий факт командой нельзя. Либо добавить его заново через `/remember 📌 ...` и удалить старый через `/forget` (порядок фактов изменится), либо поправить `facts/<user_id>.json` руками. Файл читается при каждом запросе, поэтому закрепление действует сразу. Если при ручной правке менялся порядок или число строк, индекс нужно пересоздать, это делает любой `/remember` или `/forget`. Сейчас закреплённых фактов нет, а при 132 фактах поиск выключен, так что поведение в проде не изменилось.

Проверено: 18 тестов с моками в `tests/test_pinned_facts.py` (маркер, порядок, дубли, лимит, предупреждение на 41 закреплённом, fallback при ошибке БД, `/remember` и восстановление из копии) и SQL с исключением индексов на реальной базе 14.11.2026 (вектор запроса взят из самой таблицы, Voyage не вызывался). В живом чате с включённым поиском закрепление не проверялось: поиск сейчас выключен.

Известное ограничение. Короткие справочные факты (имена, город, внешность) мало похожи на запрос вроде «сцена: ссора», поэтому при включённом поиске они могут не попасть в выдачу. Прогон слепого теста 14.11.2026 с одним запросом и лимитом 0 показал: в промпт попадало 30 фактов из 132, а из восьми ключевых фактов (имена, город, внешность) в выдачу попадало от 0 до 3 на кейс (подробнее в [EVALS.md](EVALS.md)). Лекарство: закрепить такие факты маркером 📌. Бот сам не отличает справочные факты от остальных, закреплять нужно вручную.

## Память сцен

Хранение. Две таблицы в базе `klgpff`, создаются при первом подключении, как `facts`. `scenes`: `id bigserial`, `user_id`, `created_at`, `request`, `text`, `text_hash`, уникальность `(user_id, text_hash)`. `scene_chunks`: `id`, `scene_id` (внешний ключ с `ON DELETE CASCADE`), `user_id`, `chunk_index`, `chunk_text`, `embedding vector(512)`. Отдельной колонки с номером сцены нет: номер это позиция среди сцен пользователя по `id`, ту же позицию показывают `/scenes`, `/unkeep` и метки `[сцена N]` в промпте. После удаления номера следующих сцен сдвигаются.

Сохранение (`rag.save_scene`). Порядок: проверка дубля по хэшу текста (SHA-256 от текста без крайних пробелов), эмбеддинги чанков (Voyage, `input_type=document`, пачками по 64), затем одна транзакция: строка сцены и все чанки. Сбой Voyage или БД до коммита ничего не оставляет. Дубль не сохраняется и не эмбеддится, бот называет номер уже сохранённой сцены. Параллельный `/keep` одной и той же сцены ловится `ON CONFLICT DO NOTHING`.

Чанки (`rag.chunk_scene`). Абзацы (разделитель: пустая строка) копятся, пока чанк не перевалил бы за 350 слов, абзац не режется. Абзац длиннее 350 слов остаётся одним чанком. Хвост короче 100 слов приклеивается к предыдущему чанку, если тот не раздуется выше 450. Склейка чанков возвращает абзацы сцены в исходном порядке.

Что бот берёт за сцену (`/keep`). Ответом на сообщение бота: текст этого сообщения. Длинный ответ уходит в Telegram несколькими сообщениями, и связи между ними у Telegram нет, поэтому `_generate_and_reply` помнит в памяти процесса соответствие `message_id части → полный текст ответа` (последние 200 сообщений). `/keep` в ответ на любую часть берёт сцену целиком. После перезапуска бота соответствия нет, тогда сохраняется только то сообщение, на которое ответили. Без ответа: последнее сообщение ассистента из истории. `request` это сообщение пользователя перед этим ответом (префикс команды `/scene` вырезается, до 500 символов), если ответа в истории нет, то первые 60 символов текста. Ответ на сообщение не от бота отклоняется.

Поиск (`rag.search_scenes`). Те же запросы, что строит `retrieval_queries` (текущее сообщение и контекст). Эмбеддинг запросов одним батчем, на каждый запрос top-k чанков по `<=>` среди чанков пользователя, дубли склеиваются по лучшей близости, в итоге `SCENE_TOP_K` самых близких. Порога близости нет: если сцены есть, всегда вернутся `SCENE_TOP_K` чанков, насколько бы они ни были далеки. Если у пользователя нет чанков, поиск возвращает пустой список без вызова Voyage. ANN-индекса нет, точный перебор, по тем же причинам, что для фактов.

Выжимка и хроника сюжета. В `scenes` есть колонка `summary text` (миграция `ALTER TABLE scenes ADD COLUMN IF NOT EXISTS summary text` при первом подключении, как остальные таблицы). `/done` и `/keep` после сохранения сцены вызывают `summarize_saved_scene`: `make_summary` делает один вызов `client.messages.create` в `asyncio.to_thread` с моделью `SUMMARY_MODEL` (по умолчанию `claude-haiku-5-5`), `max_tokens` 800, коротким system (`SUMMARY_SYSTEM`: до 150 слов, кто участвует, где и когда, что произошло, как изменились отношения и состояние героев, какие линии открыты, нейтрально, без откровенных подробностей, без выдумок), на тексте сцены (до 60000 символов); `rag.set_summary` пишет результат сцене по порядковому номеру. Порядок такой: сцена сохраняется первой, выжимка потом, поэтому сбой выжимки сохранение не затрагивает. Неудача (исключение вызова, `stop_reason=max_tokens`, пустой ответ, сбой записи) это одна строка пользователю «выжимка не получилась» и warning без текста; обрезанная выжимка не сохраняется. Исчерпанный дневной лимит пропускает выжимку молча (warning). Ответ длиннее `SUMMARY_MAX_CHARS` (1500) обрезается как страховка. Дубль сцены, у которой выжимки нет, получает её при повторном сохранении, дубль с выжимкой нового вызова не делает. Стоимость идёт через `add_usage` под моделью выжимки, поэтому она в `/cost` и в `spent_today`. Если `SUMMARY_MODEL` задан ID, которого нет в `MODELS`, цена по алиасу не определена и в лимит не попадёт.

Хроника (`rag.story_chronicle`, `get_story`, `select_chronicle`, `build_story_block`). SQL: `row_number() OVER (ORDER BY id)` по всем сценам юзера и отбор непустых выжимок, поэтому номер в хронике равен номеру в `/scenes`. Порядок хроники равен порядку сохранения (порядок `id`), а не порядку сюжета. `select_chronicle` идёт с самых свежих и берёт выжимки, пока их не больше `STORY_MAX_SCENES` (30) и пока суммарный размер строк `N. выжимка` не больше `STORY_MAX_CHARS` (12000); остаток (ранние) отбрасывается, в блоке пометка «ранних сцен не вошло в хронику: K». Блок `<story_so_far>` собирает `build_story_block`, `build_messages` дописывает его к последнему user-сообщению в порядке канон, хроника, фрагменты `<memory_scenes>`; в `system` и в более ранние сообщения блок не попадает, префикс кеша не меняется. `get_story` возвращает пусто без обращения к БД, когда память сцен выключена (по умолчанию) или лимиты нулевые; при ошибке БД warning и запрос без блока. Блок и хроника целиком идут в каждый запрос после точки кеширования, то есть оплачиваются как обычный input: полная хроника (30 сцен по ~150 слов) это порядка нескольких тысяч токенов. Замеров нет. `/scenes N` читает одну выжимку из БД и не вызывает модель, `/context` показывает число сцен в хронике, их размер в символах, число сцен без выжимки и, если лимит обрезает хронику, сколько сцен войдёт.

Инъекция фрагментов. `build_scenes_block`

Включение. По умолчанию подмешивание выключено для каждого пользователя: `get_memory_scenes` сразу возвращает пустой список, поиск и БД не вызываются, в запрос идут только промпт и факты. Переключатель `/context scenes on|off`, состояние в файле `models/<user_id>.scenes` (`on` или `off`, нет файла значит выкл), рядом с режимом модели, том `models/` смонтирован. Команды `/keep`, `/scenes`, `/unkeep`, таблицы и индексация от переключателя не зависят.

Деградация. Память сцен выключена, нет сцен, `SCENE_TOP_K=0`, нет запросов, или поиск бросил исключение (Postgres недоступен, нет ключа Voyage): блок не добавляется, запрос идёт без него, при исключении в лог пишется warning с типом ошибки. Падения запроса из-за памяти сцен нет. Исключение при `/keep`, `/scenes` и `/unkeep` превращается в сообщение «недоступна/не удалось», в ops-тред при сбое `/keep` уходит предупреждение.

Цена. Когда у пользователя есть сохранённые сцены, на каждый запрос добавляется один вызов Voyage (эмбеддинг двух поисковых запросов) и несколько тысяч токенов во входе (до 3 чанков по 250-350 слов). Эти токены стоят в хвосте после точки кеширования, поэтому всегда оплачиваются как обычный input. Замеров я не делал. Пока сцен нет, ни Voyage, ни токенов это не стоит.

Импорт сцены пересылкой. Сцену, которая пришла несколькими сообщениями или написана до памяти сцен, можно сохранить, переслав её сообщения боту. Признак: `message.forward_origin` типа `user`, где `sender_user.id` равен id самого бота (в установленных PTB 22.5 и 22.8 приходит только `forward_origin`; старых `forward_from` и `forward_date` в этих версиях в Message нет, код их проверяет через `getattr` на случай другой версии). `handle_message` проверяет это раньше всего остального: такое сообщение не попадает ни в историю, ни в классификатор, ни в модель, а кладётся в `forward_buffers[user_id]`, бот отвечает «часть N принята». Порядок частей: дата исходного сообщения из `forward_origin.date`, при равной дате (точность до секунды) порядок прихода. Дубль по хэшу текста не добавляется. `/keep` без ответа при непустом буфере склеивает части через пустую строку (так бот и резал длинный ответ), сохраняет обычным `rag.save_scene` (чанки, эмбеддинги, дубль по хэшу) и после успеха или «уже сохранена» очищает буфер; при ошибке БД буфер остаётся. `/keep` ответом на сообщение буфер не трогает. Буфер в памяти процесса, после рестарта пуст, сбрасывается по `/new`, после `/keep` и через `FORWARD_BUFFER_TTL` (30 минут) после последней части. Часть длиннее 3500 символов буфером принимается.

Доступ. Все три команды работают через `is_allowed`. Пока `ALLOWED_USERS` задана, чужой пользователь не получает ответа, в базу команды не доходят. Как и везде в боте, пустая `ALLOWED_USERS` открывает бота всем.

Проверено: тесты на моках в `tests/test_scenes.py` (чанкер, дубли, запись без потери чанков и порядок «эмбеддинги, потом запись», нумерация `/scenes` и `/unkeep`, молчание для чужого ID, пустая память не меняет запрос, блок после канона и в хвосте, запрос без блока при ошибке поиска, `scenes=` в логе); три мутации (сдвиг нумерации, потеря чанка, блок в `system` или перед каноном) валят тесты. SQL проверен 15.11.2026 на реальной базе `klgpff` синтетическими one-hot векторами, Voyage не вызывался: сохранение, дубль, чанки без потерь, список, поиск по двум запросам, откат при сбое посреди записи, удаление каскадом, сдвиг номеров, изоляция пользователей (26 проверок). Тестовые строки удалены, таблицы после проверки пусты. Дамп `klgpff` содержит таблицы `scenes` и `scene_chunks`.

## Роутер

`classify_message` вызывает Haiku с `max_tokens=4` и системным промптом `CLASSIFIER_PROMPT`. Решение принимается по тому, что должен содержать ответ:

- opus: новая проза с нуля (сцена, рассказ, глава), включая голые запросы вроде «сцена про них» и «ещё одну»;
- sonnet: проза на основе существующего текста (продолжить, переписать, сократить, добавить деталь);
- haiku: только если ответ не проза для чтения (вопросы о героях или фактах, планирование, мета-разговор).

В сомнительных случаях sonnet. Ответ разбирается поиском подстроки `opus`, `sonnet`, `haiku`. При исключении, пустом ответе или ответе без этих слов возвращается sonnet, при исключении ещё уходит предупреждение в ops-тред.

Режим по умолчанию теперь opus, роутер не вызывается. Он включается командой `/model auto`. Причина: слепой тест моделей (см. [EVALS.md](EVALS.md)): в первом прогоне opus выиграл 5 кейсов из 8, во втором 3 из 3 у haiku. Кроме того, 14.11.2026 роутер отправил на haiku запрос, на который пришёл ответ в 11575 символов (до исправления `CLASSIFIER_PROMPT`). `/scene` всегда идёт на Opus. `/regenerate` в режиме `auto` берёт модель из `CLAUDE_MODEL`, роутер там не работает.

## Цены

Таблица `PRICING` в коде, доллары за миллион токенов, ноябрь 2026. Значения сверял автор по странице цен Anthropic, я их не проверял.

| Модель | input | output | cache write (1 час) | cache read |
|---|---|---|---|---|
| Opus 5.5 | 4.00 | 20.00 | 8.00 | 0.20 |
| Sonnet 5.5 | 2.00 | 10.00 | 4.00 | 0.10 |
| Haiku 5.5 | 0.10 | 0.50 | 0.20 | 0.01 |

Цена записи в кеш считается из input: умножить на 2 для TTL 1 час, на 1.25 для 5 минут (`cost_for_model`). Для Haiku цены указаны для промпта до 100K токенов, выше он дороже (по комментарию в коде, нашего размера это не касается). Таблица привязана к алиасам `opus`, `sonnet`, `haiku`, а не к ID моделей: при смене версии в `.env` расчёт не ломается. Токены учитываются в `usage/<chat_id>.json` по ID модели в четырёх корзинах: input, output, cache read, cache write. Старые ID (Opus 4.8, Sonnet 4.6 и другие) сопоставляются с алиасами, чтобы `/cost` не терял прошлые расходы. По каждой модели `/cost` показывает долю попаданий в кеш, `cache_read / (input + cache_read)`: это быстрая проверка, что кеш работает.

## Импорт текста и кандидаты в факты

Режим `/import`. Состояние лежит в том же буфере `forward_buffers[user_id]`, что и пересланные части, с флагом `import`. Пока флаг стоит, `handle_message` кладёт в буфер любое текстовое сообщение (и пересылку, и чужую), `handle_document` кладёт документ `.txt` или `.md`; модель, роутер и извлечение не вызываются, порог `MAX_INPUT_CHARS` не действует, ответ «часть N, M слов» без LLM. Дата для порядка: у пересылки от бота `forward_origin.date`, у остального дата самого сообщения. Дубль по хэшу текста не добавляется. Буфер ограничен `IMPORT_BUFFER_MAX_CHARS` = 60000 символов, считая по склеенному тексту, то есть с `\n\n` между частями (часть, которая не помещается, отклоняется с пояснением, мелкая следующая ещё может поместиться). Документ: расширение `.txt` или `.md`, размер до 200 КБ (проверяется по метаданным и по скачанным байтам), декодирование `utf-8-sig` без подмены символов (не UTF-8 отклоняется), подпись к файлу не читается. Вне режима `.txt` и `.md` не скачиваются и не обрабатываются, бот отвечает отказом с подсказкой; прочие типы файлов игнорируются, как раньше.

Выход. `/done` склеивает буфер (`\n\n`, порядок как у пересылки), сохраняет через `rag.save_scene` (дубль по `text_hash` не пишется, называется номер уже сохранённой), очищает буфер и режим, запускает извлечение. Если БД недоступна, буфер и режим остаются, `/done` можно повторить. `/cancel` и `/new` очищают буфер и режим без сохранения и извлечения. Таймаут `FORWARD_BUFFER_TTL` (30 минут без новых частей): буфер удаляется, режим гаснет, пользователь попадает в `import_expired` и на следующее сообщение или документ получает одно уведомление, само сообщение не обрабатывается (иначе часть фанфика ушла бы в модель). `/done` и `/cancel` после таймаута тоже сообщают о нём. `/keep` без ответа во время `/import` отправляет на `/done`.

Извлечение (`run_extraction`, модуль `extract.py`). Когда: после `/done` (на склеенном тексте) и после каждого ответа бота от `EXTRACT_MIN_WORDS` слов (300), после отправки сцены и до записи строки `done:`. Один вызов `client.messages.create` в `asyncio.to_thread` с моделью `EXTRACT_MODEL` (по умолчанию `claude-haiku-5-5`), `max_tokens` `EXTRACT_MAX_TOKENS` (3000; при 1500 ответ на большой сцене обрезался, 15.11.2026), коротким system (текст в `extract.EXTRACT_SYSTEM`) и сообщением с каноном списком и сценой (до 60000 символов). Ответ разбирает `parse_extraction`: JSON целиком или текст от первой `{` до последней `}`, нестроковые элементы выбрасываются, не больше 8 фактов и 5 противоречий; нераспознанный ответ это warning в лог и тишина. Если `stop_reason` равен `max_tokens`, берутся полные элементы массивов (`extract.salvage_truncated`: оборванный последний элемент отбрасывается, warning с числом взятых); если не нашлось ни одного, пользователь один раз получает «извлечение фактов оборвалось, попробуй /extract N» (после `/done` буфера уже нет, поэтому подсказка ведёт на `/extract` с номером сохранённой сцены; у сцены, которую бот написал и пользователь ещё не сохранил: «сохрани сцену командой /keep и запусти /extract <номер>»), в лог warning, повторного вызова нет. Промпт просит компактный JSON, короткие факты, не больше 8 фактов и 5 противоречий. Любое исключение внутри извлечения гасится (warning, без текста), на ответ пользователю оно не влияет. Дедупликация: нормализованное совпадение (регистр, `ё`=`е`, знаки, маркер 📌) с фактами, ожидающими кандидатами и между собой; затем `rag.filter_similar`: Voyage-эмбеддинги кандидатов и ожидающих (`input_type=document`), косинус к существующим фактам считается в SQL по уже сохранённым эмбеддингам (`1 - min(embedding <=> q)`), к ожидающим и уже оставленным кандидатам в Python; порог `SIM_DEDUP` (0.92) включительно считается дублем. Если проверка близости упала, остаётся нормализованная дедупликация. Стоимость: `add_usage` под моделью извлечения, поэтому она в `/cost` и в `spent_today`; при исчерпанном дневном лимите извлечение пропускается молча (warning). В `done:` добавлено `extracted=N extract_cost=$X` (кандидатов показано, цена вызова). Если `EXTRACT_MODEL` задан ID, которого нет в `MODELS`, цена по алиасу не определена и в лимит не попадёт.

Кандидаты (`fact_candidates`). Таблица в базе `klgpff`: `id`, `user_id`, `created_at`, `num`, `text`, `status` (`pending` или `accepted`). `num` это номер для `/accept`, счётчик на пользователя (`max(num)+1` среди живых строк), а не позиция в списке: когда более ранняя партия сгорает, номера в сообщениях о поздней не съезжают. Срок жизни 24 часа: просроченное удаляется при любом обращении к таблице (`DELETE ... created_at < now() - interval '24 hours'`). Если сгорели все строки, нумерация начинается с единицы заново, поэтому номера из сообщения старше суток считаются недействительными.

`/accept`. `rag.claim_candidates` одним `UPDATE ... SET status='accepted' ... WHERE status='pending' ... RETURNING` забирает выбранные (или все ожидающие) строки: повторный вызов с теми же номерами ничего не берёт и сообщает «уже приняты раньше», неизвестные номера сообщает отдельно. Затем бот дописывает тексты в `facts/<user_id>.json` (`save_facts`: файл и копия в `backups/facts/`) и переиндексирует факты (`reindex_user_facts`), то есть тем же путём, что `/remember`. Если запись файла упала, строки возвращаются в `pending` (`release_candidates`). В факты ничего не попадает без `/accept`: модель может выдумать деталь или принять разовое событие сюжета за постоянный факт, а факты обязательны в каждом запросе.

Проверено: тесты с моками в `tests/test_import_mode.py` и `tests/test_extraction.py` (части и пересылки идут в буфер без вызова клиента Anthropic, `/done` склеивает, сохраняет и запускает извлечение, `/cancel`, `/new`, таймаут, лимит буфера, документы, чужой ID; парсинг JSON, битый JSON, не больше 8, порог слов, `EXTRACT_ENABLED=false`, дедупликация, стоимость в usage и `/cost`, пропуск при лимите; `/accept` all и номера, индексация, неверные номера, повтор, откат при сбое записи; по умолчанию блока `<memory_scenes>` нет, `/context scenes on|off`, `/context` не вызывает модель и не печатает тексты). Мутации, которые валят тесты: извлечение без `/done`, запись фактов без `/accept`, вызов модели в режиме `/import`, блок сцен при выключенной памяти, вызов модели из `/context`, документ вне `/import` в модель, снятые лимиты буфера и файла, снятый таймаут, неучтённая стоимость извлечения. SQL `fact_candidates` и `filter_similar` проверен 15.11.2026 на реальной базе `klgpff` синтетическими one-hot векторами, Voyage не вызывался: нумерация, claim подмножества, повтор, release, срок жизни (просроченное удаляется и не берётся), изоляция пользователей, отсев по близости к факту, к ожидающему и внутри партии (26 проверок). Тестовые строки удалены, реальные факты не тронуты (132 строки до и после).

Причина обрыва и исправление (15.11.2026). На `/done` сцены в 9927 слов извлечение оборвалось с `stop_reason=max_tokens` при `max_tokens=3000` (до этого при 1500 то же самое на другой сцене). Из счётчиков расхода: выход вызова ровно 3000 токенов (вход ~31.6k, $0.0047, в логе $0.0046), тогда как выжимка той же сцены уложилась в ~526 токенов. `salvage_truncated` не нашёл ни одного полного элемента JSON, то есть видимого JSON почти не было. Это согласуется с тем, что токены размышления Haiku 5.5 (включено по умолчанию, при omitted `thinking` модель думает сама) входят в `max_tokens` и съели лимит: вывод упирается в потолок независимо от его величины, поэтому подъём потолка и нарезка сцены на куски причину не лечат (нарезка ещё умножила бы стоимость на число кусков). Типы блоков ответа (`thinking` или `text`) в тот раз не логировались, поэтому вывод косвенный. Исправление: выжимка и извлечение вызываются с `thinking: {"type": "disabled"}` (`aux_call_kwargs`, переключатель `AUX_THINKING`: `disabled` по умолчанию, `adaptive` возвращает поведение модели по умолчанию), и каждый такой вызов пишет в лог `extraction call:` или `summary call:` со `stop`, `in`, `out` и перечнем типов блоков (`blocks=thinking,text`), без текста: если причина окажется другой, это будет видно сразу.

`/extract <номер>` (`cmd_extract`). Берёт полный текст сохранённой сцены (`rag.get_scene_text`, номер как в `/scenes`) и запускает тот же `run_extraction`, что после `/done`: проверка дневного лимита с ответом пользователю, строка «извлекаю…», затем список кандидатов или «новых фактов в тексте не найдено». Для явных команд (`/done`, `/extract`) сбой разбора или вызова не молчит, а даёт «извлечение фактов не получилось, подробности в логе»; для сцен, написанных ботом, сбой по-прежнему молчит. Повторный запуск не дублирует кандидатов (дедупликация против ожидающих). Команда ничего не пишет в факты, только `/accept`.

## Длинный запрос (`/prompt` и `/go`)

Зачем. Пересказ до 20000 символов должен уйти в модель одним запросом, а не пятью. Защита от рассыпанной вставки (`MAX_INPUT_CHARS`, окно вставки) при этом остаётся включённой: длинный текст проходит только по явному маршруту.

Состояние. Тот же буфер `forward_buffers[user_id]`, что у `/import`, с новым флагом `prompt` (флаги взаимоисключающие). `collect_mode(user_id)` возвращает `"import"`, `"prompt"` или `None`; `handle_message` и `handle_document` кладут любой текст и `.txt`/`.md` в буфер, если режим не `None`, до `paste_check`. Модель, роутер и извлечение при сборе не вызываются. Потолок `PROMPT_BUFFER_MAX_CHARS` = 20000 считается в `add_part` по склеенному тексту (с разделителем `\n\n`), поэтому запрос после склейки не длиннее 20000. Таймаут тот же `FORWARD_BUFFER_TTL`, уведомление идёт через `prompt_expired` в `notify_import_expired`. `/cancel`, `/new` и `clear_import` чистят буфер обоих режимов. `/import` при включённом `/prompt` (и наоборот) отказывает; если в буфере лежат пересланные части сцены для `/keep`, `/prompt` не стартует, пока их не сохранят или не сбросят: молча стирать их нельзя, подмешивать в запрос тоже.

`/go` (`cmd_go`), порядок проверок: белый список; режим включён (иначе «режим /prompt не включён»); буфер не пуст (режим остаётся); `block_if_over_limit` (буфер остаётся целым, модель не зовётся, строки со стоимостью нет). Затем строка «N символов в одном запросе, ≈ $A–B…» (`estimate_prompt_cost`: `PROMPT_CHARS_PER_TOKEN` = 2.8 символа на токен, ответ `PROMPT_OUT_TOKENS` = 5000–10000, вход без кэша, цены `PRICING`; в режиме `auto` считается по Opus, и строка так и говорит), `clear_import` (второй `/go` ничего не отправит) и `_process_user_text(update, text, log_text=False)`: тот же путь, что у обычного сообщения (классификатор в `auto`, `_generate_and_reply`, канон, хроника, кэш), но в лог вместо первых 80 символов идёт только длина. Если после этого последним в истории остался сам запрос (ошибка API, пустой ответ), он убирается из истории, буфер и режим возвращаются, бот просит повторить `/go`: иначе 20 тысяч символов пришлось бы набирать заново, а `/regenerate` без ответа в истории не работает.

Стоимость запроса в 20000 символов (≈ 7100 токенов входа) с ответом 5–10 тысяч токенов на Opus 5.5 ($4 вход, $20 выход за миллион): ≈ $0.13–0.23 без канона и хроники (вход $0.029, выход $0.10–0.20). Канон и хроника дописываются в хвост последнего сообщения пользователя, то есть уходят без кэша: каждые 5000 токенов добавляют ≈ $0.02. Кэш. Точка кэширования стоит на предпоследнем сообщении (ответ ассистента), а не на самом запросе (`build_messages`), поэтому первая генерация и повтор через `/regenerate` платят за запрос полную цену входа и почти не отличаются по стоимости: кэш экономит только system и историю до прошлого ответа. Выход (≈ 80% цены) кэшем не удешевляется вовсе. Зато на следующем обычном сообщении запрос и ответ (≈ 12–17 тысяч токенов) становятся префиксом: один раз запись в кэш на 1 час по $8 за миллион (≈ $0.10–0.14), дальше чтение по $0.20 за миллион (≈ $0.003 за сообщение) против $0.05–0.07 при обычном входе. Запись отбивается на втором сообщении после ответа, с третьего кэш экономит, если `trim_history` не обрезал историю (после 16 сообщений остаётся 8).

Проверено: `tests/test_prompt_mode.py` (50 тестов с моками, без сети): сбор не вызывает клиент Anthropic, роутер и извлечение; `/go` вызывает `client.messages.stream` ровно один раз со склеенным по дате текстом, с каноном и `cache_control` у system; повторный `/go`, `/go` без режима и с пустым буфером модель не зовут; граница буфера (ровно 20000 с разделителями проходит, 20001 нет); дневной лимит блокирует до строки со стоимостью и оставляет буфер, под лимитом и при `DAILY_LIMIT_USD=0` проходит; чужой ID получает тишину и не может отправить чужой буфер; таймаут, `/cancel`, `/new`; взаимоисключение с `/import` и пересланными частями; возврат буфера после сбоя; текст запроса не попадает ни в лог, ни в ответы. Мутационная проверка: 26 мутаций (снятые проверки лимита, режима, белого списка, пустого буфера, очистки буфера, двойной вызов, неучтённые разделители, порог 3500, логирование текста и другие), все убиты тестами.

## Защита от дорогих запросов

Случай, из-за которого это появилось: сцена, вставленная в чат десятью частями по лимиту Telegram, запустила Opus с размышлением на каждую часть, ушло $3 и месячный лимит Anthropic.

Дневной лимит. `add_usage` пишет токены не только в общий счётчик по моделям, но и в `usage/<chat_id>.json` под ключом `_daily` (дата по UTC+3, модель, bucket). Верхний уровень файла с суммами по моделям остался как был, `/cost` его читает по-прежнему, служебные ключи с `_` пропускает. `spent_today` берёт bucket'ы за сегодня и считает цену той же `cost_for_model`, что и `/cost`. `block_if_over_limit` стоит перед каждым входом в модель: в `_process_user_text` (до истории и классификатора), в `/scene`, в `/regenerate` и ещё раз в `_generate_and_reply` на всякий случай. Расход известен только после ответа, поэтому один запрос может выйти за лимит: это ограничитель, а не бюджет. Лимит считается на чат (счётчики и так по чату), при одном авторе это то же, что на пользователя. `_daily` режется до 60 дней. Старые файлы без `_daily` читаются: за сегодня расход ноль, поэтому в день выката дневной счёт начался с нуля. `DAILY_LIMIT_USD <= 0` выключает проверку. Блокировка пишет warning (`daily limit reached`) без текста запроса.

Порог длины. В `handle_message` обычное сообщение длиннее `MAX_INPUT_CHARS = 4000` символов (потолок сообщения Telegram 4096) не уходит в модель, ответ фиксированный («длинный текст не отправлен; для длинного запроса: /prompt, части (или .txt), /go. Для сохранения сцены: /import, части, /done»), в лог только длина. Команды порогом не ограничены (у них отдельный фильтр PTB). Пересланные от бота части и любые сообщения в режимах `/import` и `/prompt` проверяются раньше и порог не затрагивают. Документы в модель не идут вообще (см. «Импорт текста»).

Окно вставки (`paste_check`, `paste_state[user_id]`). Порог проверял каждое сообщение отдельно, поэтому хвост длинной вставки короче порога уходил в Opus (инцидент 15.11.2026: 14 кусков по ~4000 символов отклонены при тогдашнем пороге 3500, 15-й прошёл, $0.31; после подъёма порога до 4000 кусок Telegram в 4096 символов по-прежнему отклоняется). Теперь отказ по порогу открывает окно `PASTE_WINDOW_SECONDS` (15 секунд): следующие обычные текстовые сообщения этого пользователя в окне глотаются молча, каждое продлевает окно (скользящее), в лог одна строка `paste window: message swallowed (#N, M chars)` без текста. Ответ пользователю только на первое отклонение. Быстрое правило: два обычных сообщения с интервалом меньше `PASTE_FAST_SECONDS` (1 с) считаются вставкой и открывают то же окно с ответом «несколько сообщений подряд не отправлены; для длинного запроса: /prompt…». Время берётся из даты сообщения Telegram, не из момента обработки: пока бот ждёт ответ модели, очередь стоит, и по часам обработки окно не работало бы. Дата Telegram с точностью до секунды, поэтому «интервал меньше секунды» означает одну и ту же секунду. Окно проверяется в `handle_message` после ветки режимов `/import` и `/prompt` и ветки пересылки, поэтому на команды, документы, пересылки от бота и оба режима не действует. Ограничение: первое сообщение быстрой вставки (когда ни одно не превысило порог) уже ушло в модель к моменту, когда правило срабатывает. `PASTE_WINDOW_SECONDS=0` выключает окно и быстрое правило.

Проверено: 40 тестов с моками в `tests/test_import_limit.py` (части вперемешку склеиваются по дате, пересланная часть не вызывает клиент Anthropic и роутер, дубль, `/new`, таймаут буфера, чужой ID, сохранение через настоящий `rag.save_scene`; исчерпанный лимит не вызывает клиент, под лимитом вызывает, граница ровно на лимите, граница суток по UTC+3, `/cost` с лимитом, длинное сообщение не вызывает модель).

## Лог команд

Хук `log_command` стоит в группе -1 (до основных хендлеров) и на каждое сообщение-команду пишет в лог одну строку: `⌨️ command /<имя> user=<id>`. Текст сообщения не логируется. Хук ничего не блокирует, команды обрабатываются как обычно. В лог попадают и неизвестные команды, и команды от пользователей вне белого списка. Подсчёт за период: `docker logs klgpff-bot-klgpff-bot-1 2>&1 | grep 'command /' | awk '{print $5}' | sort | uniq -c`. Логи Docker живут, пока жив контейнер, а он пересоздаётся при каждом деплое, поэтому для подсчёта за неделю нужен период без деплоев либо выгрузка логов перед деплоем.

## Хранение и перезапуск

Сцены (память сцен) лежат только в Postgres, файлов у них нет, из `facts/*.json` их не восстановить. Базу `klgpff` целиком дампит `ops/backup.sh` из heylark-infra раз в сутки.

Остальное изменяемое состояние лежит в файлах (в том числе `models/<user_id>.scenes`, переключатель памяти сцен). Буфер частей, режимы `/import` и `/prompt` и соответствие частей длинного ответа живут только в памяти процесса. Кандидаты в факты лежат в Postgres 24 часа и в архив бэкапов попадают вместе с базой `klgpff`, которые пишутся сразу при изменении (таблица в [README](../README.md#хранение)). `usage/` смонтирована отдельным volume, поэтому счётчики `/cost` переживают пересоздание контейнера. `PicklePersistence` из `python-telegram-bot` не используется: он сбрасывает данные на диск по интервалу и при остановке, и при перезапуске в этот момент свежая правка промпта потерялась бы. История диалога (`conversations`) хранится только в памяти: после перезапуска контекст пустой, факты и промпт сохраняются.

## Решения и их цена

**Anthropic API напрямую.** Нужны стабильный системный промпт, выбор модели под задачу, свой `max_tokens` и кеш. Цена: авторизация, повторы, учёт расходов и замена устаревших моделей на мне.

**Один Postgres с pgvector вместо отдельной векторной БД.** Фактов сотни, точный перебор быстр и без потерь, одним сервисом меньше. До 14.11.2026 векторы лежали в Qdrant, его контейнер и тома удалены, архив томов остался на сервере. Цена: Postgres общий с другим проектом. У роли `klgpff` права ограничены: она не читает таблицы чужих баз и не создаёт там объекты (проверено 14.11.2026), но `CONNECT` к другим базам кластера у неё есть, потому что по умолчанию он выдан `PUBLIC`.

**Файлы для фактов.** Источник правды `facts/<user_id>.json`, индекс в БД производный и пересоздаётся. Цена: нет защиты от одновременной записи, при одном авторе она не нужна.

**ID моделей в окружении, цены по алиасу.** Жёстко прописанный ID Opus однажды стал отдавать 404 и потребовал правки кода и деплоя. Сейчас это строка в `.env`.

**Стриминг основной генерации.** Иначе длинная сцена при большом `max_tokens` упирается в десятиминутный предел SDK. Урезать `max_tokens` не подходит: короче становятся сцены.

## Известные ограничения

- При фактах выше 150 справочные факты (имена, город, внешность) могут не попасть в промпт, пока они не закреплены 📌. Закреплять нужно вручную, командой существующий факт закрепить нельзя.
- В боте нет команды для просмотра системного промпта: он лежит в `prompts/<chat_id>.txt` на сервере. Список фактов показывает `/facts`.
- Метрика «противоречий канону» в слепом тесте считается судьёй, который сам модель (Sonnet). Если поиск включён, судья видит тот же урезанный список фактов, что и модель, поэтому нарушений по фактам, которые не попали в выдачу, он не заметит.
- Автоматические тесты есть только на выдачу и закрепление фактов (`tests/test_pinned_facts.py`), на `/facts` (`tests/test_facts_command.py`), на набор команд и лог команд (`tests/test_commands.py`), на память сцен (`tests/test_scenes.py`), на импорт пересылкой и защиту от расходов (`tests/test_import_limit.py`), на выжимки и хронику сюжета (`tests/test_story.py`), на вспомогательные вызовы и `/extract` (`tests/test_extract_command.py`), на режим `/prompt` и `/go` (`tests/test_prompt_mode.py`); запуск описан в [README](../README.md#запуск). Остальной код тестами не покрыт, для него проверки `pyflakes` и импорт модуля. Для сравнения моделей есть скрипты в `evals/`.
- Качество подтягивания сцен не измерено. Я не проверял, что чанки по 250-350 слов и `SCENE_TOP_K` дают полезную справку, а не шум (поэтому фрагменты по умолчанию выключены). Порога близости нет: при включённых фрагментах всегда подмешиваются ближайшие чанки, даже если ни один не подходит. Слепого теста с памятью сцен и без неё не было.
- Качество хроники не измерено. Выжимки пишет модель и они могут содержать неточности или выдумки (а при отказе модели на откровенной сцене может прийти не выжимка, а текст отказа): проверять их надо вручную через `/scenes N`. Порядок хроники равен порядку сохранения, не порядку сюжета: первую по сюжету сцену надо импортировать первой, переставить сцены нельзя (только удалить `/unkeep` и сохранить заново). Сцены, сохранённые до появления выжимок, в хронику не попадают, пока их не сохранили повторно.
- Соответствие частей длинного ответа и полного текста для `/keep` живёт в памяти процесса: после перезапуска `/keep` в ответ на часть сохранит только эту часть.
- Номер сцены это позиция в списке, а не постоянный идентификатор: после `/unkeep` номера следующих сцен сдвигаются, и метки `[сцена N]` в промпте тоже.
- При старте в логе предупреждение `PTBUserWarning` про `heartbeat_loop`: задача создаётся до запуска приложения. Heartbeat при этом пишется и healthcheck зелёный, причину я не разбирал.
- Расширение `vector` в этой базе версии 0.8.7, а в базе `nexus_arcana` 0.8.3. Это разные базы, обновление одной не трогает другую.
- Дневной лимит не видит расходов, понесённых до его появления, и не считает траты за пределами этого бота (например, прямые вызовы API тем же ключом). Месячный лимит Anthropic он не заменяет.
- Порог длины ввода считает символы, а не токены. Документы в модель не идут вовсе, а в режимах `/import` и `/prompt` порога нет, там действует лимит буфера (60000 и 20000 символов). Оценка стоимости перед `/go` грубая (2.8 символа на токен, ответ 5–10 тысяч токенов, без канона и хроники), реальные токены пишутся в `/cost` после ответа; на размышления модели при больших ответах оценка не рассчитана.
- Качество извлечения кандидатов в факты не измерено: я не сверял, какую долю предложенного автор принимает, сколько полезного модель пропускает и насколько точно она находит противоречия канону. Подмешивание сцен (см. выше) тоже не измерено.
- Дедупликация кандидатов по близости работает по эмбеддингам Voyage и порогу 0.92, подобранному без замеров. Короткие факты и перефразировки могут пройти или, наоборот, отсеяться зря. Отсев по близости к существующим фактам опирается на индекс `facts`: если он устарел или пуст, отсеивается только точное совпадение.
- Кандидаты живут 24 часа в Postgres: не принятые за сутки пропадают, номера из сообщения старше суток недействительны.
- Синхронная генерация блокирует обработку других сообщений на время ответа модели: клиент Anthropic вызывается синхронно, PTB обрабатывает апдейты по очереди, поэтому команды и сообщения, отправленные во время ответа (у длинной сцены это минуты), ждут в очереди и обрабатываются после него. Из-за этого `/import`, отправленный во время генерации, срабатывает с задержкой.
- Окно вставки не ловит вставку из коротких сообщений, ни одно из которых не превышает порог: первое такое сообщение уходит в модель.
- Причина обрыва извлечения установлена косвенно (по числам расхода и по тому, что в ответе не нашлось полного JSON-элемента), а не по типам блоков: тогда они не логировались. Исправление (выключенное размышление) на реальном вызове не проверено, только на моках. Если и после него `extraction call:` покажет `stop=max_tokens`, смотреть `blocks=` в логе.
- Роутер `/model auto` вызывает Haiku с `max_tokens=4` и без отключения размышления: при включённом по умолчанию размышлении ответ может оказаться пустым, и роутер вернёт запасной sonnet. По умолчанию режим opus, роутер не используется, поэтому я это не менял и не проверял.
