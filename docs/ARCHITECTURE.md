# Архитектура klgpff

Описание кода, как он есть в репозитории. Цифры из прогонов и логов помечены датой. Что я не проверял, написано прямо.

## Из чего состоит

Python 3.11, `python-telegram-bot` (polling), Anthropic SDK напрямую, Voyage для эмбеддингов, Postgres 16 с pgvector для поиска по фактам, остальное состояние в файлах. Один процесс, один контейнер. Postgres общий: контейнер `nexus-arcana-db`, у бота там своя база `klgpff` и своя роль. Бот подключён к docker-сети этого контейнера.

```
Telegram → handler
         → режим модели (по умолчанию opus; auto запускает роутер на Haiku)
         → факты: все, если их не больше FACTS_FULL_LIMIT, иначе поиск в pgvector
         → память сцен: top-k чанков сохранённых сцен (если есть)
         → system (статичный) + история + канон и справка из сцен в хвосте последнего сообщения
         → Anthropic Messages API, стриминг
         → ответ порциями до 4096 символов
```

## Путь одного сообщения

1. Проверка белого списка `ALLOWED_USERS`. Если переменная пуста, бот открыт всем.
2. Сообщение, пересланное от самого бота, в модель не идёт: уходит в буфер частей сцены (см. «Память сцен»). Обычное сообщение длиннее `MAX_INPUT_CHARS` (3500) получает отказ без вызова модели. Если дневной лимит исчерпан, отказ тоже без вызова. Иначе текст сообщения (или содержимое присланного `.txt`) добавляется в историю, история обрезается.
3. Режим модели читается из `models/<chat_id>.txt`. Нет файла: opus. Режим `auto`: вызывается классификатор.
4. `get_relevant_facts` возвращает факты и строку `source` для лога. `get_memory_scenes` возвращает фрагменты сцен (пусто, если сцен нет или поиск упал).
5. `build_messages` собирает запрос (канон, затем блок `<memory_scenes>` в хвосте последнего сообщения), `system_block` оборачивает системный промпт.
6. Генерация идёт через `client.messages.stream`, `max_tokens` по умолчанию 32000. Стриминг нужен потому, что SDK отказывается от запросов без стрима, которые могут идти дольше 10 минут.
7. Из ответа `response_text()` склеивает только text-блоки.
8. Пустой текст: в историю ничего не пишется, пользователь получает «пустой ответ (stop_reason=...)», в ops-тред уходит предупреждение со `stop_reason`, usage и моделью.
9. Ответ режется по абзацам до 4096 символов и уходит сообщениями.
10. В лог пишется строка `done:` с числом символов, токенами, `cache r`/`w`, ценой и `scenes=<число подмешанных чанков>`.

Короткие вызовы (классификатор) идут без стрима.

## Модель и размышления

Opus 5.5 в `content` отдаёт `ThinkingBlock` первым блоком. Раньше код брал `content[0].text` и падал на блоке без `.text`. Сейчас везде используется `response_text()`.

Токены размышления в ответе не видны, но входят в `output_tokens` и оплачиваются как output. Косвенное подтверждение из лога 14.11.2026: ответ 1625 символов и `1.8k out`. Для русского текста такой длины это заметно меньше, остальное похоже на размышления. Точной разбивки API не даёт, поэтому это оценка, а не измерение.

Если при `stop_reason=max_tokens` текста нет, значит, весь бюджет ушёл на размышления. Бот в этом случае отвечает «пустой ответ» и не пишет ничего в историю.

## Кеширование

- `system` статичный: только текст системного промпта чата, с `cache_control` типа `ephemeral` и TTL 1 час (`CACHE_TTL`, можно `5m`).
- Канон в `system` не попадает. Его дописывает `build_messages` к концу последнего сообщения пользователя. Поэтому набор фактов может меняться от запроса к запросу, а префикс (system и история) остаётся тем же.
- Точка кеширования стоит на последнем ответе ассистента: кешируется всё до него. Канон в историю в памяти не записывается.
- История обрезается пачкой. Когда набирается `MAX_HISTORY` пар (8), остаются последние `HISTORY_KEEP` (4). При скользящем окне префикс менялся бы на каждом ходу и кеш не попадал бы никогда.
- Запись в кеш с TTL 1 час стоит два input, чтение пять или десять процентов input (см. цены).

Проверка по логам, 14.11.2026, sonnet, шесть запросов подряд: `cache r` каждого запроса равен `r + w` предыдущего (3355 + 750 = 4105, 4105 + 439 = 4544, 4544 + 541 = 5085, 5085 + 639 = 5724). 3355 токенов это системный промпт. Кеш растёт ровно на приращение каждого хода.

## Факты

Хранение. Источник правды: `facts/<user_id>.json`, JSON-список строк в порядке добавления. При каждой записи копия пишется в `backups/facts/<user_id>.json`. Если при старте рабочий файл пуст, а копия нет, файл восстанавливается из копии.

`/facts` показывает список в формате `N. текст`, где N это позиция строки в `facts/<user_id>.json` с единицы, то есть номер, который принимает `/forget`. Список режется на сообщения по границам фактов, не больше 3800 символов в сообщении (`FACTS_MSG_LIMIT`). Один факт длиннее 3800 символов режется по символам, остаток идёт следующим сообщением без номера. Если фактов нет, бот отвечает подсказкой про `/remember`.

Индекс. Таблица `facts` в базе `klgpff`: `user_id bigint`, `fact_index integer`, `fact_text text`, `embedding vector(512)`, первичный ключ `(user_id, fact_index)`. Эмбеддинги Voyage `voyage-3-lite` (512 измерений). Расширение `vector` создаёт админ БД, у роли бота прав на это нет. Индекс пересоздаётся целиком: при `/remember`, `/forget`, при восстановлении из копии и при первом обращении, если индекс пуст. Эмбеддинги считаются до транзакции, замена атомарна: если Voyage недоступен, старый индекс остаётся.

Поиск. Точный перебор по косинусному расстоянию (`<=>`), ANN-индекса нет. По комментарию в `rag.py` HNSW имеет смысл от десятков тысяч строк, у меня 132, замеров скорости я не делал. Запросов два: текущее сообщение (до 1500 символов) и контекст (две предыдущие реплики пользователя и первые 800 символов последнего ответа, всего до 2000). Первое сообщение чата даёт один запрос. На каждый запрос берётся 30 ближайших (`RAG_TOP_K`), результаты склеиваются без дублей, остаётся не больше 50 лучших (`RAG_MAX_FACTS`), порядок возвращается авторский, по `fact_index`.

Порог. Пока фактов не больше `FACTS_FULL_LIMIT` (150), поиск не используется, модель получает все факты, в логе `source` равен `all (<= 150)`. Сейчас фактов 132, то есть в проде поиск не работает вообще. Он включается, когда фактов станет больше 150, или при `FACTS_FULL_LIMIT=0`.

Деградация. Если БД недоступна или нет ключа Voyage, бот отдаёт все факты (`source` вида `fallback`) и шлёт предупреждение в ops-тред. Пустой индекс заполняется заново из файла.

Закреплённые факты. Факт, который начинается с маркера 📌 (например, `/remember 📌 у героини шрам`), закреплён. В `facts/<user_id>.json` он хранится как есть, с маркером, `/facts` показывает его тоже с маркером. Когда поиск включён (фактов больше `FACTS_FULL_LIMIT`), выдача собирается так: сначала все закреплённые в авторском порядке, потом результат поиска. Закреплённые исключаются из SQL-запроса по `fact_index`, поэтому не занимают места в `RAG_TOP_K` и `RAG_MAX_FACTS`: при трёх закреплённых и `RAG_MAX_FACTS=50` в промпт уйдёт до 53 фактов. Дублей нет: если индекс устарел, совпадающие по тексту факты отбрасываются. Маркер не попадает ни в канон, ни в текст для эмбеддинга (везде `strip_pin`: он убирает маркер и пробелы или variation selector после него). Если закреплённых больше 40, в лог пишется предупреждение. Пока фактов не больше `FACTS_FULL_LIMIT`, маркер ничего не меняет, все факты и так идут в промпт. В `source` закреплённые видны как `semantic (N queries) + K pinned`, без них формат прежний. Если все факты закреплены, поиск не вызывается (`all pinned`).

Закрепить уже существующий факт командой нельзя. Либо добавить его заново через `/remember 📌 ...` и удалить старый через `/forget` (порядок фактов изменится), либо поправить `facts/<user_id>.json` руками. Файл читается при каждом запросе, поэтому закрепление действует сразу. Если при ручной правке менялся порядок или число строк, индекс нужно пересоздать, это делает любой `/remember` или `/forget`. Сейчас закреплённых фактов нет, а при 132 фактах поиск выключен, так что поведение в проде не изменилось.

Проверено: 18 тестов с моками в `tests/test_pinned_facts.py` (маркер, порядок, дубли, лимит, предупреждение на 41 закреплённом, fallback при ошибке БД, `/remember` и восстановление из копии) и SQL с исключением индексов на реальной базе 14.11.2026 (вектор запроса взят из самой таблицы, Voyage не вызывался). В живом чате с включённым поиском закрепление не проверялось: поиск сейчас выключен.

Известное ограничение. Короткие справочные факты (имена, город, внешность) мало похожи на запрос вроде «сцена: ссора», поэтому при включённом поиске они могут не попасть в выдачу. Прогон слепого теста 14.11.2026 с одним запросом и лимитом 0 показал: в промпт попадало 30 фактов из 132, а из восьми ключевых фактов (имена, город, внешность) в выдачу попадало от 0 до 3 на кейс (подробнее в [EVALS.md](EVALS.md)). Лекарство: закрепить такие факты маркером 📌. Бот сам не отличает справочные факты от остальных, закреплять нужно вручную.

## Память сцен

Хранение. Две таблицы в базе `klgpff`, создаются при первом подключении, как `facts`. `scenes`: `id bigserial`, `user_id`, `created_at`, `request`, `text`, `text_hash`, уникальность `(user_id, text_hash)`. `scene_chunks`: `id`, `scene_id` (внешний ключ с `ON DELETE CASCADE`), `user_id`, `chunk_index`, `chunk_text`, `embedding vector(512)`. Отдельной колонки с номером сцены нет: номер это позиция среди сцен пользователя по `id`, ту же позицию показывают `/scenes`, `/unkeep` и метки `[сцена N]` в промпте. После удаления номера следующих сцен сдвигаются.

Сохранение (`rag.save_scene`). Порядок: проверка дубля по хэшу текста (SHA-256 от текста без крайних пробелов), эмбеддинги чанков (Voyage, `input_type=document`, пачками по 64), затем одна транзакция: строка сцены и все чанки. Сбой Voyage или БД до коммита ничего не оставляет. Дубль не сохраняется и не эмбеддится, бот называет номер уже сохранённой сцены. Параллельный `/keep` одной и той же сцены ловится `ON CONFLICT DO NOTHING`.

Чанки (`rag.chunk_scene`). Абзацы (разделитель: пустая строка) копятся, пока чанк не перевалил бы за 350 слов, абзац не режется. Абзац длиннее 350 слов остаётся одним чанком. Хвост короче 100 слов приклеивается к предыдущему чанку, если тот не раздуется выше 450. Склейка чанков возвращает абзацы сцены в исходном порядке.

Что бот берёт за сцену (`/keep`). Ответом на сообщение бота: текст этого сообщения. Длинный ответ уходит в Telegram несколькими сообщениями, и связи между ними у Telegram нет, поэтому `_generate_and_reply` помнит в памяти процесса соответствие `message_id части → полный текст ответа` (последние 200 сообщений). `/keep` в ответ на любую часть берёт сцену целиком. После перезапуска бота соответствия нет, тогда сохраняется только то сообщение, на которое ответили. Без ответа: последнее сообщение ассистента из истории. `request` это сообщение пользователя перед этим ответом (префикс команды `/scene` вырезается, до 500 символов), если ответа в истории нет, то первые 60 символов текста. Ответ на сообщение не от бота отклоняется.

Поиск (`rag.search_scenes`). Те же запросы, что строит `retrieval_queries` (текущее сообщение и контекст). Эмбеддинг запросов одним батчем, на каждый запрос top-k чанков по `<=>` среди чанков пользователя, дубли склеиваются по лучшей близости, в итоге `SCENE_TOP_K` самых близких. Порога близости нет: если сцены есть, всегда вернутся `SCENE_TOP_K` чанков, насколько бы они ни были далеки. Если у пользователя нет чанков, поиск возвращает пустой список без вызова Voyage. ANN-индекса нет, точный перебор, по тем же причинам, что для фактов.

Инъекция. `build_scenes_block` собирает блок `<memory_scenes>`: текст «Фрагменты ранее сохранённых сцен автора. Это не канон. Если они противоречат <canon>, прав канон. Используй для преемственности (события, интонация, детали отношений), не пересказывай и не копируй дословно.» и фрагменты с пометкой `[сцена N]`. `build_messages` дописывает его в конец последнего user-сообщения после канона. В `system` и в более ранние сообщения блок не попадает, префикс кеша не меняется. Сцены не попадают в историю в памяти и в логи (в `done:` только число чанков).

Деградация. Нет сцен, `SCENE_TOP_K=0`, нет запросов, или поиск бросил исключение (Postgres недоступен, нет ключа Voyage): блок не добавляется, запрос идёт без него, при исключении в лог пишется warning с типом ошибки. Падения запроса из-за памяти сцен нет. Исключение при `/keep`, `/scenes` и `/unkeep` превращается в сообщение «недоступна/не удалось», в ops-тред при сбое `/keep` уходит предупреждение.

Цена. Когда у пользователя есть сохранённые сцены, на каждый запрос добавляется один вызов Voyage (эмбеддинг двух поисковых запросов) и несколько тысяч токенов во входе (до 3 чанков по 250-350 слов). Эти токены стоят в хвосте после точки кеширования, поэтому всегда оплачиваются как обычный input. Замеров я не делал. Пока сцен нет, ни Voyage, ни токенов это не стоит.

Импорт сцены пересылкой. Сцену, которая пришла несколькими сообщениями или написана до памяти сцен, можно сохранить, переслав её сообщения боту. Признак: `message.forward_origin` типа `user`, где `sender_user.id` равен id самого бота (в установленных PTB 22.5 и 22.8 приходит только `forward_origin`; старых `forward_from` и `forward_date` в этих версиях в Message нет, код их проверяет через `getattr` на случай другой версии). `handle_message` проверяет это раньше всего остального: такое сообщение не попадает ни в историю, ни в классификатор, ни в модель, а кладётся в `forward_buffers[user_id]`, бот отвечает «часть N принята». Порядок частей: дата исходного сообщения из `forward_origin.date`, при равной дате (точность до секунды) порядок прихода. Дубль по хэшу текста не добавляется. `/keep` без ответа при непустом буфере склеивает части через пустую строку (так бот и резал длинный ответ), сохраняет обычным `rag.save_scene` (чанки, эмбеддинги, дубль по хэшу) и после успеха или «уже сохранена» очищает буфер; при ошибке БД буфер остаётся. `/keep` ответом на сообщение буфер не трогает. Буфер в памяти процесса, после рестарта пуст, сбрасывается по `/new`, после `/keep` и через `FORWARD_BUFFER_TTL` (30 минут) после последней части. Часть длиннее 3500 символов буфером принимается.

Доступ. Все три команды работают через `is_allowed`. Пока `ALLOWED_USERS` задана, чужой пользователь не получает ответа, в базу команды не доходят. Как и везде в боте, пустая `ALLOWED_USERS` открывает бота всем.

Проверено: тесты на моках в `tests/test_scenes.py` (чанкер, дубли, запись без потери чанков и порядок «эмбеддинги, потом запись», нумерация `/scenes` и `/unkeep`, молчание для чужого ID, пустая память не меняет запрос, блок после канона и в хвосте, запрос без блока при ошибке поиска, `scenes=` в логе); три мутации (сдвиг нумерации, потеря чанка, блок в `system` или перед каноном) валят тесты. SQL проверен 15.11.2026 на реальной базе `klgpff` синтетическими one-hot векторами, Voyage не вызывался: сохранение, дубль, чанки без потерь, список, поиск по двум запросам, откат при сбое посреди записи, удаление каскадом, сдвиг номеров, изоляция пользователей (26 проверок). Тестовые строки удалены, таблицы после проверки пусты. Дамп `klgpff` содержит таблицы `scenes` и `scene_chunks`.

## Роутер

`classify_message` вызывает Haiku с `max_tokens=4` и системным промптом `CLASSIFIER_PROMPT`. Решение принимается по тому, что должен содержать ответ:

- opus: новая проза с нуля (сцена, рассказ, глава), включая голые запросы вроде «сцена про них» и «ещё одну»;
- sonnet: проза на основе существующего текста (продолжить, переписать, сократить, добавить деталь);
- haiku: только если ответ не проза для чтения (вопросы о героях или фактах, планирование, мета-разговор).

В сомнительных случаях sonnet. Ответ разбирается поиском подстроки `opus`, `sonnet`, `haiku`. При исключении, пустом ответе или ответе без этих слов возвращается sonnet, при исключении ещё уходит предупреждение в ops-тред.

Режим по умолчанию теперь opus, роутер не вызывается. Он включается командой `/model auto`. Причина: слепой тест моделей (см. [EVALS.md](EVALS.md)): в первом прогоне opus выиграл 5 кейсов из 8, во втором 3 из 3 у haiku. Кроме того, 14.11.2026 роутер отправил на haiku запрос, на который пришёл ответ в 11575 символов (до исправления `CLASSIFIER_PROMPT`). `/scene` всегда идёт на Opus. `/regenerate` в режиме `auto` берёт модель из `CLAUDE_MODEL`, роутер там не работает.

| Модель | input | output | cache write (1 час) | cache read |
|---|---|---|---|---|
| Opus 5.5 | 4.00 | 20.00 | 8.00 | 0.20 |
| Sonnet 5.5 | 2.00 | 10.00 | 4.00 | 0.10 |
| Haiku 5.5 | 0.10 | 0.50 | 0.20 | 0.01 |

Цена записи в кеш считается из input: умножить на 2 для TTL 1 час, на 1.25 для 5 минут (`cost_for_model`). Для Haiku цены указаны для промпта до 100K токенов, выше он дороже (по комментарию в коде, нашего размера это не касается). Таблица привязана к алиасам `opus`, `sonnet`, `haiku`, а не к ID моделей: при смене версии в `.env` расчёт не ломается. Токены учитываются в `usage/<chat_id>.json` по ID модели в четырёх корзинах: input, output, cache read, cache write. Старые ID (Opus 4.8, Sonnet 4.6 и другие) сопоставляются с алиасами, чтобы `/cost` не терял прошлые расходы. По каждой модели `/cost` показывает долю попаданий в кеш, `cache_read / (input + cache_read)`: это быстрая проверка, что кеш работает.

## Защита от дорогих запросов

Случай, из-за которого это появилось: сцена, вставленная в чат десятью частями по лимиту Telegram, запустила Opus с размышлением на каждую часть, ушло $3 и месячный лимит Anthropic.

Дневной лимит. `add_usage` пишет токены не только в общий счётчик по моделям, но и в `usage/<chat_id>.json` под ключом `_daily` (дата по UTC+3, модель, bucket). Верхний уровень файла с суммами по моделям остался как был, `/cost` его читает по-прежнему, служебные ключи с `_` пропускает. `spent_today` берёт bucket'ы за сегодня и считает цену той же `cost_for_model`, что и `/cost`. `block_if_over_limit` стоит перед каждым входом в модель: в `_process_user_text` (до истории и классификатора), в `/scene`, в `/regenerate` и ещё раз в `_generate_and_reply` на всякий случай. Расход известен только после ответа, поэтому один запрос может выйти за лимит: это ограничитель, а не бюджет. Лимит считается на чат (счётчики и так по чату), при одном авторе это то же, что на пользователя. `_daily` режется до 60 дней. Старые файлы без `_daily` читаются: за сегодня расход ноль, поэтому в день выката дневной счёт начался с нуля. `DAILY_LIMIT_USD <= 0` выключает проверку. Блокировка пишет warning (`daily limit reached`) без текста запроса.

Порог длины. В `handle_message` обычное сообщение длиннее `MAX_INPUT_CHARS = 3500` символов не уходит в модель, ответ фиксированный, в лог только длина. Команды порогом не ограничены (у них отдельный фильтр PTB). Пересланные от бота части проверяются раньше и порог не затрагивают. Присланный документ `.txt` идёт мимо порога и подчиняется только дневному лимиту: это явное действие, а не вставка. Если порог нужен и для документов, его надо ставить в `_process_user_text`.

Проверено: 40 тестов с моками в `tests/test_import_limit.py` (части вперемешку склеиваются по дате, пересланная часть не вызывает клиент Anthropic и роутер, дубль, `/new`, таймаут буфера, чужой ID, сохранение через настоящий `rag.save_scene`; исчерпанный лимит не вызывает клиент, под лимитом вызывает, граница ровно на лимите, граница суток по UTC+3, `/cost` с лимитом, длинное сообщение не вызывает модель).

## Лог команд

Хук `log_command` стоит в группе -1 (до основных хендлеров) и на каждое сообщение-команду пишет в лог одну строку: `⌨️ command /<имя> user=<id>`. Текст сообщения не логируется. Хук ничего не блокирует, команды обрабатываются как обычно. В лог попадают и неизвестные команды, и команды от пользователей вне белого списка. Подсчёт за период: `docker logs klgpff-bot-klgpff-bot-1 2>&1 | grep 'command /' | awk '{print $5}' | sort | uniq -c`. Логи Docker живут, пока жив контейнер, а он пересоздаётся при каждом деплое, поэтому для подсчёта за неделю нужен период без деплоев либо выгрузка логов перед деплоем.

## Хранение и перезапуск

Сцены (память сцен) лежат только в Postgres, файлов у них нет, из `facts/*.json` их не восстановить. Базу `klgpff` целиком дампит `ops/backup.sh` из heylark-infra раз в сутки.

Остальное изменяемое состояние лежит в файлах, которые пишутся сразу при изменении (таблица в [README](../README.md#хранение)). `usage/` смонтирована отдельным volume, поэтому счётчики `/cost` переживают пересоздание контейнера. `PicklePersistence` из `python-telegram-bot` не используется: он сбрасывает данные на диск по интервалу и при остановке, и при перезапуске в этот момент свежая правка промпта потерялась бы. История диалога (`conversations`) хранится только в памяти: после перезапуска контекст пустой, факты и промпт сохраняются.

## Решения и их цена

**Anthropic API напрямую.** Нужны стабильный системный промпт, выбор модели под задачу, свой `max_tokens` и кеш. Цена: авторизация, повторы, учёт расходов и замена устаревших моделей на мне.

**Один Postgres с pgvector вместо отдельной векторной БД.** Фактов сотни, точный перебор быстр и без потерь, одним сервисом меньше. До 14.11.2026 векторы лежали в Qdrant, его контейнер и тома удалены, архив томов остался на сервере. Цена: Postgres общий с другим проектом. У роли `klgpff` права ограничены: она не читает таблицы чужих баз и не создаёт там объекты (проверено 14.11.2026), но `CONNECT` к другим базам кластера у неё есть, потому что по умолчанию он выдан `PUBLIC`.

**Файлы для фактов.** Источник правды `facts/<user_id>.json`, индекс в БД производный и пересоздаётся. Цена: нет защиты от одновременной записи, при одном авторе она не нужна.

**ID моделей в окружении, цены по алиасу.** Жёстко прописанный ID Opus однажды стал отдавать 404 и потребовал правки кода и деплоя. Сейчас это строка в `.env`.

**Стриминг основной генерации.** Иначе длинная сцена при большом `max_tokens` упирается в десятиминутный предел SDK. Урезать `max_tokens` не подходит: короче становятся сцены.

## Известные ограничения

- При фактах выше 150 справочные факты (имена, город, внешность) могут не попасть в промпт, пока они не закреплены 📌. Закреплять нужно вручную, командой существующий факт закрепить нельзя.
- В боте нет команды для просмотра системного промпта: он лежит в `prompts/<chat_id>.txt` на сервере. Список фактов показывает `/facts`.
- Метрика «противоречий канону» в слепом тесте считается судьёй, который сам модель (Sonnet). Если поиск включён, судья видит тот же урезанный список фактов, что и модель, поэтому нарушений по фактам, которые не попали в выдачу, он не заметит.
- Автоматические тесты есть только на выдачу и закрепление фактов (`tests/test_pinned_facts.py`), на `/facts` (`tests/test_facts_command.py`), на набор команд и лог команд (`tests/test_commands.py`), на память сцен (`tests/test_scenes.py`), на импорт пересылкой и защиту от расходов (`tests/test_import_limit.py`); запуск описан в [README](../README.md#запуск). Остальной код тестами не покрыт, для него проверки `pyflakes` и импорт модуля. Для сравнения моделей есть скрипты в `evals/`.
- Качество подтягивания сцен не измерено. Я не проверял, что `SCENE_TOP_K=3` и чанки по 250-350 слов дают полезную справку, а не шум. Порога близости нет: при любом запросе подмешиваются три ближайших чанка, даже если ни один не подходит. Слепого теста с памятью сцен и без неё не было.
- Соответствие частей длинного ответа и полного текста для `/keep` живёт в памяти процесса: после перезапуска `/keep` в ответ на часть сохранит только эту часть.
- Номер сцены это позиция в списке, а не постоянный идентификатор: после `/unkeep` номера следующих сцен сдвигаются, и метки `[сцена N]` в промпте тоже.
- При старте в логе предупреждение `PTBUserWarning` про `heartbeat_loop`: задача создаётся до запуска приложения. Heartbeat при этом пишется и healthcheck зелёный, причину я не разбирал.
- Расширение `vector` в этой базе версии 0.8.7, а в базе `nexus_arcana` 0.8.3. Это разные базы, обновление одной не трогает другую.
- Дневной лимит не видит расходов, понесённых до его появления, и не считает траты за пределами этого бота (например, прямые вызовы API тем же ключом). Месячный лимит Anthropic он не заменяет.
- Порог длины ввода считает символы, а не токены, и не касается документов `.txt`.
