# klgpff

Telegram-бот для длинной художественной прозы. Ходит в Anthropic API напрямую, держит канон персонажей и мира (факты) и подмешивает его в каждый запрос, считает расходы. Один автор, доступ по белому списку Telegram ID.

## Что делает

- Пишет сцены через Opus 5.5. Это режим по умолчанию. Роутер на Haiku, который выбирает модель под запрос, включается командой `/model auto`.
- Канон. Пока фактов не больше `FACTS_FULL_LIMIT` (150), в запрос идут все. Выше лимита включается поиск по pgvector. Сейчас фактов 132, поэтому поиск в проде не работает.
- Закреплённые факты. Факт, который начинается с 📌, при включённом поиске попадает в запрос всегда и не занимает места в лимите поиска. Закреплённых сейчас нет.
- Память сцен. Удачную сцену можно сохранить командой `/keep`. Сохранённые сцены режутся на чанки и индексируются в pgvector. К каждому новому запросу бот подмешивает до `SCENE_TOP_K` (3) самых близких чанков как справку. Подробности ниже.
- Prompt cache: статичный system, история с точкой кеширования на последнем ответе, канон в хвосте последнего сообщения пользователя. TTL 1 час.
- Учёт расходов по чату: `/cost` показывает input, output, cache read и write по каждой модели. Счётчики лежат в `usage/` на хосте и переживают пересоздание контейнера.
- Лог команд: каждая команда пишет в лог одну строку с именем и user_id, без текста сообщения.
- Системный промпт у каждого чата свой, переживает перезапуск.
- Текстовый файл, присланный документом, обрабатывается как обычное сообщение (подпись, если есть, идёт в начало).

Чего больше нет: сохранения длинных ответов в `outputs/` и отправки их файлом, команды `/last`. Ответ длиннее 4096 символов режется по абзацам на несколько сообщений.

## Команды

| Команда | Что делает |
|---|---|
| `/new` | Сбросить контекст диалога (факты остаются) |
| `/scene <описание>` | Длинная сцена на Opus, от 1500 слов, независимо от режима |
| `/regenerate [правка]` | Перегенерировать последний ответ, можно с правкой |
| `/remember <факт>` | Запомнить факт. Если текст начинается с 📌, факт закреплён |
| `/forget <номер>` | Забыть факт по номеру |
| `/forget all` | Забыть все факты |
| `/facts` | Показать все факты с номерами, теми же, что принимает `/forget`. Закреплённые идут с 📌. Длинный список режется на несколько сообщений по границам фактов |
| `/keep` | Сохранить сцену в память. Ответом на сообщение бота: берётся оно (если сцена пришла несколькими сообщениями и бот их помнит, то целиком). Без ответа: если боту пересланы его же сообщения (см. ниже), склеенная из них сцена, иначе последний ответ бота. Бот отвечает номером сцены, дубль не сохраняется |
| `/scenes` | Сохранённые сцены: номер, дата, запрос (до 60 символов), число слов. Длинный список режется на сообщения по границам строк |
| `/unkeep <номер>` | Удалить сцену с этим номером из `/scenes` вместе с чанками. Номера после неё сдвигаются |
| `/addprompt <текст>` | Дописать к системному промпту |
| `/model` | Показать режим |
| `/model opus\|sonnet\|haiku` | Закрепить модель, роутер выключен (по умолчанию opus) |
| `/model auto` | Модель выбирает роутер |
| `/cost` | Расходы по этому чату, расход за сегодня и дневной лимит |
| `/help` | Список команд |

## Запуск

Сервер: Docker Compose. Образ `python:3.11-slim`, бот подключён к docker-сети контейнера Postgres. Переменные окружения описаны в `.env.example`.

```bash
cp .env.example .env   # заполнить токены и DATABASE_URL
docker compose up -d --build klgpff-bot
```

Локально: `pip install -r requirements.txt` и `python claude_tg_bot.py`. Поиск по фактам требует Postgres с расширением `vector` и ключ Voyage. Без них бот работает, но отдаёт в промпт все факты. Скрипты в `evals/` требуют Python 3.10 или новее.

Тесты (выдача и закрепление фактов, `/facts`, набор команд и лог команд, память сцен, импорт пересылкой, дневной лимит; на моках, без сети и без API):

```bash
TELEGRAM_BOT_TOKEN=1:a ANTHROPIC_API_KEY=x python3 -m unittest discover -s tests -v
```

Деплой: GitHub Actions по пушу в `main` заходит на сервер по SSH, делает `git pull` и `docker compose up -d --build klgpff-bot`. Healthcheck считает бота живым, пока файл `/tmp/heartbeat` обновлялся меньше 90 секунд назад.

## Хранение

| Путь | Содержимое |
|---|---|
| `facts/<user_id>.json` | Факты пользователя, JSON-список строк. Закреплённый факт начинается с 📌 |
| `prompts/<chat_id>.txt` | Системный промпт чата |
| `models/<chat_id>.txt` | Режим модели: opus, sonnet, haiku или auto |
| `usage/<chat_id>.json` | Счётчики токенов по моделям для `/cost` и разбивка по дням (`_daily`) для дневного лимита (отдельный volume) |
| `backups/facts/<user_id>.json` | Копия фактов, пишется при каждом изменении |
| `backups/archive/` | Шифрованные архивы фактов и промптов |
| `eval_runs/` | Результаты слепого теста моделей (приватно) |

Всё это в `.gitignore`. Векторный индекс фактов лежит в Postgres (таблица `facts` в базе `klgpff`) и пересоздаётся из `facts/<user_id>.json`. Сцены лежат только в Postgres (таблицы `scenes` и `scene_chunks` в той же базе), файлов у них нет. История диалога хранится только в памяти процесса: после перезапуска контекст пустой.

## Память сцен

Что это. Справочник из сцен, которые автор сам отметил как удачные. Сохранённая сцена режется по абзацам на чанки примерно по 250-350 слов (абзац не рвётся), чанки получают эмбеддинги Voyage `voyage-3-lite`, всё хранится в Postgres рядом с индексом фактов. Когда приходит новый запрос, бот ищет по косинусу `SCENE_TOP_K` (по умолчанию 3) ближайших чанков среди сцен этого пользователя, теми же двумя запросами, что и для фактов.

Как пользоваться.

- `/keep` в ответ на сообщение бота со сценой, или просто `/keep` сразу после неё. Ответ бота: номер сохранённой сцены. Ту же сцену второй раз не сохранить, бот скажет, под каким номером она уже лежит.
- Сцена, которая не сохранилась, потому что пришла частями, или написана до появления памяти сцен: выделите её сообщения в чате с ботом и перешлите их боту же (Forward). Бот отвечает «часть N принята» и в модель их не отправляет, расходов нет. Порядок частей берётся по дате исходных сообщений, повторно присланная часть не добавляется. Затем `/keep` без ответа: бот сохранит склеенную сцену (части через пустую строку), назовёт номер и число частей и очистит буфер. Буфер живёт в памяти бота, свой у каждого пользователя, и сбрасывается по `/new`, после `/keep` и через 30 минут без новых частей. Если сохранить не удалось (БД недоступна), буфер остаётся, `/keep` можно повторить. Пересланные не от бота сообщения обрабатываются как обычный текст.
- `/scenes` показывает список с номерами. Номер это место в списке с единицы.
- `/unkeep <номер>` удаляет сцену. Номера всех сцен после неё сдвигаются на единицу, перед следующим `/unkeep` смотрите `/scenes` заново.

Только вручную. Бот ничего не сохраняет сам. Автоматическое сохранение каждого ответа забило бы память черновиками, неудачными дублями и правками, а в справку попадало бы то, что автору не нравится. Решает автор.

Как фрагменты попадают в запрос. Блок `<memory_scenes>` дописывается в хвост последнего сообщения пользователя, сразу после `<canon>`. System и история не меняются, поэтому prompt cache работает как раньше. В блоке написано, что это справка, а не канон, и что при противоречии прав канон. Каждый фрагмент помечен `[сцена N]`. Если сцен нет или поиск упал (Postgres или Voyage недоступны), блок не добавляется, запрос уходит как без памяти сцен, в лог идёт warning.

Чем сцены не являются. Они не часть канона и не факты: в `facts/<user_id>.json` не попадают, `/facts` их не показывает, считаются только справкой для преемственности (события, интонация, детали отношений). В строке `done:` в логе есть поле `scenes=<сколько чанков подмешано>`.

## Защита от дорогих запросов

- Дневной лимит. Перед каждым обращением к Anthropic бот считает расходы чата за сегодня (дата по UTC+3, те же счётчики, что у `/cost`). Когда они достигли `DAILY_LIMIT_USD` (по умолчанию 1.00), API не вызывается, бот отвечает «дневной лимит $X исчерпан (потрачено $Y), поднять можно в .env: DAILY_LIMIT_USD», в лог идёт warning. Лимит считается по уже оплаченным запросам: один запрос может выйти за него. `DAILY_LIMIT_USD=0` выключает лимит. Расходы до появления дневной разбивки (до этого релиза) в счёт не входят: день выката начался с нуля.
- Длинный ввод. Обычное сообщение (не команда) длиннее 3500 символов (`MAX_INPUT_CHARS` в коде) в модель не уходит, бот отвечает «длинный текст не отправлен в модель, чтобы не тратить деньги; для сохранения сцены перешли её части боту и вызови /keep». Так сцена, вставленная частями по лимиту Telegram, не запускает Opus на каждую часть. Пересланные от бота части сцены порог не касается, `.txt` документом тоже (на него действует только дневной лимит).
- `/cost` показывает расход за сегодня и лимит.

## Бэкапы

Факты это единственное, что автор пишет руками, поэтому они защищены двумя способами.

- Зеркало. Каждый `/remember` и `/forget` пишет `facts/<id>.json` и копию в `backups/facts/<id>.json` (отдельный volume). При старте, если рабочий файл отсутствует или пуст, а копия непустая, бот восстанавливает файл и переиндексирует факты в pgvector. Это переживает `git reset --hard` и пересоздание volume `facts/`.
- Шифрованный архив. `scripts/backup_facts.sh` пакует `facts/` и `prompts/` в tar.gz, шифрует через `gpg` (симметрично, AES256, пароль из `BACKUP_PASSPHRASE`), кладёт в `backups/archive/facts-<время>.tar.gz.gpg` и оставляет 14 последних. На сервере запускается из cron ежедневно, пример строки crontab в шапке скрипта. Нужен `gpg` на хосте.

Сцены. Из `facts/*.json` их не восстановить: они живут только в базе `klgpff`. Эту базу целиком (вместе с `facts`, `scenes` и `scene_chunks`) каждый день дампит `ops/backup.sh` из репозитория heylark-infra (cron на сервере, `~/backups/klgpff/klgpff_<дата>.dump`, формат `pg_dump -Fc`, 14 последних). Старый `~/backups/pg_backup.sh` дампит только `nexus_arcana` и в cron не стоит.

Восстановление из архива:

```bash
gpg -d backups/archive/facts-YYYYMMDD-HHMMSS.tar.gz.gpg | tar -xzf -
```

Команда создаёт `facts/` и `prompts/` в текущем каталоге. На старых версиях `gpg` может понадобиться `gpg -d --pinentry-mode loopback --passphrase "$BACKUP_PASSPHRASE" ...`.
