# klgpff

Telegram-бот для длинной художественной прозы. Ходит в Anthropic API напрямую, держит канон персонажей и мира (факты) и подмешивает его в каждый запрос, считает расходы. Один автор, доступ по белому списку Telegram ID.

## Что делает

- Пишет сцены через Opus 5.5. Это режим по умолчанию. Роутер на Haiku, который выбирает модель под запрос, включается командой `/model auto`.
- Канон. Пока фактов не больше `FACTS_FULL_LIMIT` (150), в запрос идут все. Выше лимита включается поиск по pgvector. Сейчас фактов 132, поэтому поиск в проде не работает.
- Закреплённые факты. Факт, который начинается с 📌, при включённом поиске попадает в запрос всегда и не занимает места в лимите поиска. Закреплённых сейчас нет.
- По умолчанию в модель уходят только системный промпт и факты. Что именно уйдёт при следующем запросе, показывает `/context` (размеры, числа и режимы, без текстов, без вызова модели).
- Память сцен и хроника сюжета. Удачную сцену можно сохранить командой `/keep` (или загрузить через `/import`). При сохранении бот пишет выжимку сцены (до 150 слов), а сохранённые сцены режутся на чанки и индексируются в pgvector. Подмешивание по умолчанию выключено, включается `/context scenes on`: тогда в хвост запроса после канона идёт хроника сюжета, выжимки всех сохранённых сцен по порядку. Подробности ниже.
- Загрузка текста без расходов: `/import`, части (текстом, пересылкой или .txt/.md файлом), `/done`. Из загруженной сцены и из каждой сцены, написанной ботом, бот предлагает кандидатов в факты, в факты они попадают только по `/accept`. Подробности ниже.
- Prompt cache: статичный system, история с точкой кеширования на последнем ответе, канон в хвосте последнего сообщения пользователя. TTL 1 час.
- Учёт расходов по чату: `/cost` показывает input, output, cache read и write по каждой модели. Счётчики лежат в `usage/` на хосте и переживают пересоздание контейнера.
- Лог команд: каждая команда пишет в лог одну строку с именем и user_id, без текста сообщения.
- Системный промпт у каждого чата свой, переживает перезапуск.
- Текстовый файл, присланный документом, обрабатывается как обычное сообщение (подпись, если есть, идёт в начало).

Чего больше нет: сохранения длинных ответов в `outputs/` и отправки их файлом, команды `/last`. Ответ длиннее 4096 символов режется по абзацам на несколько сообщений.

## Команды

| Команда | Что делает |
|---|---|
| `/new` | Сбросить контекст диалога (факты остаются) |
| `/scene <описание>` | Длинная сцена на Opus, от 1500 слов, независимо от режима |
| `/regenerate [правка]` | Перегенерировать последний ответ, можно с правкой |
| `/remember <факт>` | Запомнить факт. Если текст начинается с 📌, факт закреплён |
| `/forget <номер>` | Забыть факт по номеру |
| `/forget all` | Забыть все факты |
| `/facts` | Показать все факты с номерами, теми же, что принимает `/forget`. Закреплённые идут с 📌. Длинный список режется на несколько сообщений по границам фактов |
| `/keep` | Сохранить сцену в память. Ответом на сообщение бота: берётся оно (если сцена пришла несколькими сообщениями и бот их помнит, то целиком). Без ответа: если боту пересланы его же сообщения (см. ниже), склеенная из них сцена, иначе последний ответ бота. Бот отвечает номером сцены, дубль не сохраняется |
| `/scenes` | Сохранённые сцены: номер, дата, запрос (до 60 символов), число слов, есть ли выжимка. Длинный список режется на сообщения по границам строк |
| `/scenes N` | Выжимка сцены N (без полного текста): так можно проверить, что в хронике нет выдумок |
| `/unkeep <номер>` | Удалить сцену с этим номером из `/scenes` вместе с чанками. Номера после неё сдвигаются |
| `/import` | Включить режим приёма: текст, пересылки и .txt/.md файлы идут в буфер, модель не вызывается |
| `/done` | Склеить буфер, сохранить как сцену и запустить извлечение кандидатов в факты |
| `/cancel` | Выйти из режима `/import` без сохранения, очистить буфер |
| `/extract <номер>` | Повторно найти кандидатов в факты в уже сохранённой сцене (номер как в `/scenes`), как после `/done`. Один вызов дешёвой модели, в факты ничего не попадает без `/accept` |
| `/accept <номера\|all>` | Добавить выбранных кандидатов в факты |
| `/context` | Что уйдёт в модель при следующем запросе |
| `/context scenes on\|off` | Включить или выключить подмешивание памяти сцен (по умолчанию выключено) |
| `/addprompt <текст>` | Дописать к системному промпту |
| `/model` | Показать режим |
| `/model opus\|sonnet\|haiku` | Закрепить модель, роутер выключен (по умолчанию opus) |
| `/model auto` | Модель выбирает роутер |
| `/cost` | Расходы по этому чату, расход за сегодня и дневной лимит |
| `/help` | Список команд |

## Запуск

Сервер: Docker Compose. Образ `python:3.11-slim`, бот подключён к docker-сети контейнера Postgres. Переменные окружения описаны в `.env.example`.

```bash
cp .env.example .env   # заполнить токены и DATABASE_URL
docker compose up -d --build klgpff-bot
```

Локально: `pip install -r requirements.txt` и `python claude_tg_bot.py`. Поиск по фактам требует Postgres с расширением `vector` и ключ Voyage. Без них бот работает, но отдаёт в промпт все факты. Скрипты в `evals/` требуют Python 3.10 или новее.

Тесты (выдача и закрепление фактов, `/facts`, набор команд и лог команд, память сцен, импорт пересылкой, дневной лимит, режим `/import`, `/context`, извлечение фактов, `/extract` и `/accept`, окно вставки, выжимки и хроника сюжета; на моках, без сети и без API):

```bash
TELEGRAM_BOT_TOKEN=1:a ANTHROPIC_API_KEY=x python3 -m unittest discover -s tests -v
```

Деплой: GitHub Actions по пушу в `main` заходит на сервер по SSH, делает `git pull` и `docker compose up -d --build klgpff-bot`. Healthcheck считает бота живым, пока файл `/tmp/heartbeat` обновлялся меньше 90 секунд назад.

## Хранение

| Путь | Содержимое |
|---|---|
| `facts/<user_id>.json` | Факты пользователя, JSON-список строк. Закреплённый факт начинается с 📌 |
| `prompts/<chat_id>.txt` | Системный промпт чата |
| `models/<chat_id>.txt` | Режим модели: opus, sonnet, haiku или auto |
| `models/<user_id>.scenes` | Подмешивание памяти сцен: `on` или `off` (нет файла: выкл) |
| `usage/<chat_id>.json` | Счётчики токенов по моделям для `/cost` и разбивка по дням (`_daily`) для дневного лимита (отдельный volume) |
| `backups/facts/<user_id>.json` | Копия фактов, пишется при каждом изменении |
| `backups/archive/` | Шифрованные архивы фактов и промптов |
| `eval_runs/` | Результаты слепого теста моделей (приватно) |

Всё это в `.gitignore`. Векторный индекс фактов лежит в Postgres (таблица `facts` в базе `klgpff`) и пересоздаётся из `facts/<user_id>.json`. Сцены лежат только в Postgres (таблицы `scenes` и `scene_chunks` в той же базе), файлов у них нет. История диалога хранится только в памяти процесса: после перезапуска контекст пустой.

## Память сцен

Что это. Справочник из сцен, которые автор сам отметил как удачные. Сохранённая сцена режется по абзацам на чанки примерно по 250-350 слов (абзац не рвётся), чанки получают эмбеддинги Voyage `voyage-3-lite`, всё хранится в Postgres рядом с индексом фактов. Когда приходит новый запрос, бот ищет по косинусу `SCENE_TOP_K` (по умолчанию 3) ближайших чанков среди сцен этого пользователя, теми же двумя запросами, что и для фактов.

Как пользоваться.

- `/keep` в ответ на сообщение бота со сценой, или просто `/keep` сразу после неё. Ответ бота: номер сохранённой сцены. Ту же сцену второй раз не сохранить, бот скажет, под каким номером она уже лежит.
- Сцена, которая не сохранилась, потому что пришла частями, или написана до появления памяти сцен: выделите её сообщения в чате с ботом и перешлите их боту же (Forward). Бот отвечает «часть N принята» и в модель их не отправляет, расходов нет. Порядок частей берётся по дате исходных сообщений, повторно присланная часть не добавляется. Затем `/keep` без ответа: бот сохранит склеенную сцену (части через пустую строку), назовёт номер и число частей и очистит буфер. Буфер живёт в памяти бота, свой у каждого пользователя, и сбрасывается по `/new`, после `/keep` и через 30 минут без новых частей. Если сохранить не удалось (БД недоступна), буфер остаётся, `/keep` можно повторить. Пересланные не от бота сообщения обрабатываются как обычный текст.
- `/scenes` показывает список с номерами. Номер это место в списке с единицы.
- `/unkeep <номер>` удаляет сцену. Номера всех сцен после неё сдвигаются на единицу, перед следующим `/unkeep` смотрите `/scenes` заново.

Только вручную. Бот ничего не сохраняет сам. Автоматическое сохранение каждого ответа забило бы память черновиками, неудачными дублями и правками, а в справку попадало бы то, что автору не нравится. Решает автор.

Включение. По умолчанию память сцен выключена: в запрос идут только промпт и факты, поиск по сценам и выжимки не вызываются. `/context scenes on` включает хронику сюжета для вашего пользователя, `/context scenes off` выключает. Состояние лежит в файле `models/<user_id>.scenes` и переживает перезапуск. `/keep`, `/scenes`, `/unkeep` и выжимки работают независимо от переключателя.

Выжимка при сохранении. После `/done` и `/keep` бот отдельным вызовом `SUMMARY_MODEL` (по умолчанию Haiku 5.5) пишет выжимку сцены до 150 слов: кто участвует, где и когда, что произошло, как изменились отношения и состояние героев, какие линии остались открытыми, нейтрально и без выдумок. Сцена сохраняется в любом случае: если вызов не удался или ответ оборвался, бот одной строкой пишет «выжимка не получилась» (в лог warning). Дубль сцены, у которого выжимки ещё нет, получает её при повторном сохранении. Стоимость выжимки идёт в `/cost` и в дневной лимит, при исчерпанном лимите выжимка молча пропускается.

Хроника сюжета (когда память сцен включена). Блок `<story_so_far>` дописывается в хвост последнего сообщения пользователя, после `<canon>`: выжимки сцен по порядку сохранения, пронумерованные номерами из `/scenes`. В блоке написано, что это не канон, при противоречии прав канон, сюжет надо продолжать с учётом событий и отношений, не повторяя и не пересказывая сцены. Лимиты: `STORY_MAX_SCENES` (30) сцен и `STORY_MAX_CHARS` (12000) символов; если не помещается, берутся самые свежие, а в блоке пометка, сколько ранних сцен не вошло. System и история не меняются, prompt cache работает как раньше. Сцены без выжимки в хронику не попадают. Если сцен нет, ни у одной нет выжимки или БД не отвечает, блока нет и запрос идёт как раньше. `/scenes N` показывает выжимку одной сцены, `/context` показывает, сколько сцен в хронике, их размер и сколько сцен без выжимки.

Фрагменты сцен (`<memory_scenes>`). Прежний режим: до `SCENE_TOP_K` ближайших по смыслу чанков сохранённых сцен справкой. Теперь по умолчанию выключен (`SCENE_TOP_K=0`), включается значением больше нуля и тоже только при включённой памяти сцен. Блок идёт после хроники. Каждый фрагмент помечен `[сцена N]`. Если поиск упал (Postgres или Voyage недоступны), блок не добавляется, в лог warning.

Чем сцены не являются. Они не часть канона и не факты: в `facts/<user_id>.json` не попадают, `/facts` их не показывает, считаются только справкой для преемственности (события, интонация, детали отношений). В строке `done:` в логе есть поля `scenes=<сколько фрагментов подмешано>` и `story=<сколько выжимок в хронике>`.

Факты и сцены. Факты хранят постоянное: как выглядят герои, где живут, что за отношения, привычки. Они идут в каждый запрос и обязательны к соблюдению. Память сцен хранит ход событий и подаётся как справка ниже канона: можно опереться, нельзя считать фактом, при расхождении прав канон.

Порядок и точность хроники. Порядок хроники равен порядку сохранения, а не порядку сюжета: первую по сюжету сцену импортируйте или сохраняйте первой. Выжимки пишет модель, и они могут содержать неточности, поэтому проверяйте их через `/scenes N`. Качество хроники не измерено.

## Загрузка текста и кандидаты в факты

Как загрузить фанфик или длинную сцену. Вставлять текст в чат нельзя: сообщение длиннее 3500 символов в модель не уходит.

1. `/import`. Бот отвечает «присылай части или .txt файл, в конце /done».
2. Присылайте текст: частями обычными сообщениями, пересылкой сообщений бота или файлом .txt/.md (UTF-8, до 200 КБ). Каждая часть молча попадает в буфер, бот отвечает «часть N, M слов». Модель не вызывается, денег это не стоит. Порядок частей по дате сообщения (у пересланных по дате исходного), повторная часть не добавляется. Буфер до 60000 символов, дальше бот не принимает и говорит об этом.
3. `/done`. Бот склеивает части через пустую строку, сохраняет сцену (если такая уже есть, называет её номер), выходит из режима и запускает извлечение кандидатов в факты.

`/cancel` или `/new` выходят из режима без сохранения и извлечения, буфер очищается. Через 30 минут без новых частей режим выключается сам, буфер очищается, бот сообщает об этом на следующее сообщение (оно не обрабатывается). Буфер живёт в памяти бота: после перезапуска режим выключен. Вне режима `/import` присланный .txt в модель не отправляется: бот отвечает, что файл не принят, и подсказывает `/import`.

Кандидаты в факты. После `/done` и после каждой сцены, написанной ботом (ответ от `EXTRACT_MIN_WORDS` слов, по умолчанию 300), бот один раз вызывает недорогую модель (`EXTRACT_MODEL`, по умолчанию Haiku 5.5). Модель получает канон и текст сцены и возвращает до 8 коротких фактов об обстановке, персонажах, привычках, отношениях, которые явно сказаны в тексте, и места, где текст противоречит канону. Кандидаты, совпавшие с существующими фактами или друг с другом (после нормализации текста или с косинусной близостью от `SIM_DEDUP`, по умолчанию 0.92), отбрасываются. Результат приходит отдельным сообщением после сцены: нумерованный список, противоречия канону и подсказка `/accept 1 3 5` или `/accept all`. Кандидаты живут 24 часа, остальные сгорают. Стоимость извлечения идёт в `/cost` и в дневной лимит, при исчерпанном лимите извлечение молча пропускается. Если ответ модели оборвался по `max_tokens` (`EXTRACT_MAX_TOKENS`, по умолчанию 3000), бот берёт из него полные элементы JSON; если достать нечего, один раз пишет «извлечение фактов оборвалось, попробуй /extract N» (N номер сохранённой сцены; после `/done` буфер уже пуст, поэтому подсказка ведёт на `/extract`) и повторно сам не вызывает (это ещё деньги). Вспомогательные вызовы (выжимка и извлечение) идут с выключенным размышлением модели (`AUX_THINKING`, по умолчанию `disabled`): у Haiku 5.5 размышление включено по умолчанию и его токены входят в `max_tokens`, из-за чего на длинной сцене весь лимит уходил на размышление и JSON не появлялся. Выключить: `EXTRACT_ENABLED=false`.

`/accept` добавляет выбранных кандидатов в `facts/<user_id>.json` и индекс тем же путём, что `/remember` (индексация и копия файла), и называет номера, под которыми они теперь в `/facts`. Повторный `/accept` тех же номеров ничего не дублирует.

Почему подтверждение обязательно. Модель может выдумать деталь или принять разовое событие сюжета за постоянный факт. Факты обязательны к соблюдению в каждом запросе, выдуманный факт искажал бы все следующие сцены. Поэтому без `/accept` в факты ничего не попадает.

## Защита от дорогих запросов

- Дневной лимит. Перед каждым обращением к Anthropic бот считает расходы чата за сегодня (дата по UTC+3, те же счётчики, что у `/cost`). Когда они достигли `DAILY_LIMIT_USD` (по умолчанию 2.00), API не вызывается, бот отвечает «дневной лимит $X исчерпан (потрачено $Y), поднять можно в .env: DAILY_LIMIT_USD», в лог идёт warning. Лимит считается по уже оплаченным запросам: один запрос может выйти за него. `DAILY_LIMIT_USD=0` выключает лимит. Расходы до появления дневной разбивки (до этого релиза) в счёт не входят: день выката начался с нуля.
- Длинный ввод. Обычное сообщение (не команда) длиннее 3500 символов (`MAX_INPUT_CHARS` в коде) в модель не уходит, бот отвечает «длинный текст не отправлен в модель, чтобы не тратить деньги; для сохранения сцены: /import, части (или .txt), /done». Так сцена, вставленная частями по лимиту Telegram, не запускает Opus на каждую часть. В режиме `/import` и для пересланных от бота частей порог не действует.
- Окно вставки. Telegram режет длинную вставку на много сообщений подряд, и хвост короче порога сам по себе в модель бы прошёл. Поэтому после отказа по порогу следующие обычные текстовые сообщения этого пользователя в течение `PASTE_WINDOW_SECONDS` (по умолчанию 15) тоже не идут в модель. Окно скользящее: каждое отклонённое сообщение продлевает его. Ответ приходит только на первое отклонение, остальные проглатываются молча (в лог одна строка со счётчиком, без текста). Два и больше обычных текстовых сообщения с интервалом меньше секунды тоже считаются вставкой и открывают окно (первое из них к этому моменту уже ушло в модель). Окно не действует на команды, пересланные от бота части, документы и режим `/import`. `PASTE_WINDOW_SECONDS=0` выключает окно. Документы в модель не отправляются никогда: вне `/import` бот отвечает, что файл не принят (раньше .txt уходил прямо в Opus мимо порога).
- `/cost` показывает расход за сегодня и лимит.

## Бэкапы

Факты это единственное, что автор пишет руками, поэтому они защищены двумя способами.

- Зеркало. Каждый `/remember` и `/forget` пишет `facts/<id>.json` и копию в `backups/facts/<id>.json` (отдельный volume). При старте, если рабочий файл отсутствует или пуст, а копия непустая, бот восстанавливает файл и переиндексирует факты в pgvector. Это переживает `git reset --hard` и пересоздание volume `facts/`.
- Шифрованный архив. `scripts/backup_facts.sh` пакует `facts/` и `prompts/` в tar.gz, шифрует через `gpg` (симметрично, AES256, пароль из `BACKUP_PASSPHRASE`), кладёт в `backups/archive/facts-<время>.tar.gz.gpg` и оставляет 14 последних. На сервере запускается из cron ежедневно, пример строки crontab в шапке скрипта. Нужен `gpg` на хосте.

Сцены. Из `facts/*.json` их не восстановить: они живут только в базе `klgpff`. Эту базу целиком (вместе с `facts`, `scenes` и `scene_chunks`) каждый день дампит `ops/backup.sh` из репозитория heylark-infra (cron на сервере, `~/backups/klgpff/klgpff_<дата>.dump`, формат `pg_dump -Fc`, 14 последних). Старый `~/backups/pg_backup.sh` дампит только `nexus_arcana` и в cron не стоит.

Восстановление из архива:

```bash
gpg -d backups/archive/facts-YYYYMMDD-HHMMSS.tar.gz.gpg | tar -xzf -
```

Команда создаёт `facts/` и `prompts/` в текущем каталоге. На старых версиях `gpg` может понадобиться `gpg -d --pinentry-mode loopback --passphrase "$BACKUP_PASSPHRASE" ...`.
